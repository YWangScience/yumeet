# 第 14 章 · 迁移、路线图与开源策略

替代 Indico 的前提是让存量数据能走过来:本章给出 Indico 到 yuMeet 的字段级实体映射、可重跑的迁移流水线与校验清单;随后是通用导入导出格式、以周为粒度的 MVP 路线图与 v1/v2 版本边界、许可证与插件市场的商业策略,以及与四个竞品的逐维度对照——迁移器与对照表共同回答同一个问题:用户为什么换、怎么换、换的成本是多少。

## 14.1 Indico 迁移器

迁移器是 CLI 子命令 `yumeet migrate indico`,数据源支持两种:目标实例的 REST API(需管理员 token,适合在线增量)或 Indico 数据库导出(适合离线全量)。支持 Indico 3.0+;所有导入以 `external_id = "indico:{type}:{id}"` 做幂等 upsert,因此迁移可中断、可重跑、可在割接窗口内增量补齐。实体映射如下:

| Indico 实体 | yuMeet 实体 | 映射说明 |
| --- | --- | --- |
| Category(顶层) | `organization` | 顶层分类映射为组织(多租户模型见第 6 章) |
| Category(嵌套) | collection + tags | yuMeet 不做无限层级分类;嵌套路径转为集合与标签,原路径存 `external_path` 供检索 |
| Event(lecture / meeting / conference) | `event` | 三种类型映射为模块开关组合(见第 4 章):lecture 只开日程与资料,conference 全开 |
| Session | track + 日程 session 容器 | Indico 的 Session 兼具分轨与时段两义,拆为两个概念分别落位 |
| Contribution | `submission`(录用态)+ talk 日程条目 | 讲者、时长、材料随迁;未排期的 Contribution 只建 submission |
| SubContribution | talk 的子条目 | 合并为同一 talk 的段落,保留原始顺序 |
| Timetable Entry / Break | schedule entry | Break 映射为 break 类型条目;时间按源时区读取后转 UTC 存储 |
| Abstract | `submission` | 状态映射:submitted→submitted,under review→under_review,accepted/rejected/withdrawn 同名对应,merged 打 merged 标记 |
| Abstract Review / Paper Review | `review` | 评分维度映射到评审配置(见第 4 章),自由文本评语全量保留 |
| Registration Form / Section / Field | `registration_form` + 自定义字段 | 字段落 JSONB 引擎(见第 9 章);不支持的字段类型降级为文本并在报告中列出 |
| Registration | `registration` | 状态映射:complete→confirmed,pending→pending_review,rejected/withdrawn 同名对应 |
| Payment(payment 插件数据) | `order` | 只迁移账目快照供对账与开票;不迁移支付网关凭证 |
| User / EventPerson | `user`(guest 身份) | 不迁移密码;用户首次访问经 magic link 验证邮箱后认领历史数据(见第 6 章) |
| ACL / Protection | 角色与能力分配 | managers→organizer,submitters→speaker;inheriting protection 展平为显式设置并在报告中标注 |
| Attachment / Folder | `file`(S3) | 目录结构转为资料库分组;记录每个文件的 SHA-256 |
| Room(rb 模块) | `room` | 只迁名称/容量/位置;房间预订系统是非目标(见第 1 章) |
| Survey | JSON 归档附件 | v2 前不原生支持问卷,原始数据完整归档不丢失 |
| Event Log | 审计日志导入条目 | 只读导入,标记来源为迁移 |
| Custom pages / 静态站 | 归档快照页面 | 作为归档内容挂到活动资料库(见第 5 章) |

迁移流程:

1. `yumeet migrate indico --source https://indico.example.org --token ...`,默认 `--dry-run`,只产出报告不写入;
2. 探测 Indico 版本与启用插件,列出 category 树供选择迁移范围;
3. **抽取**:REST API 分页拉取,附件流式下载;每类实体写入本地 staging 目录的 NDJSON(一行一实体,含源 id 与源哈希);
4. **转换**:映射为 `yumeet.export.v1` 中间格式(与 14.2 的通用导入共用);HTML 描述经 sanitizer 白名单清洗;时间统一转 UTC;
5. **媒体上传**:附件传入 MinIO/S3,逐个记录 SHA-256;
6. **导入**:按依赖序(organization → user → event → form → registration → submission → schedule → file)全量 upsert;任一批次失败可从断点续跑;
7. 生成 301 重定向表(`/event/123/` → `/{org}/{event-slug}`,URL 规则见第 3 章),输出为 Caddy 配置片段;
8. **校验**并输出 HTML 报告;
9. 割接窗口内以 `--since`(updated_dt 游标)增量补迁,然后切换 DNS。

校验清单(dry-run 与正式迁移各跑一遍):每类实体源/目标计数一致;文件逐个 SHA-256 比对;抽样 50 个活动渲染公共页并做断链扫描;注册状态分布直方图迁移前后一致;时区抽查——每个活动的首末日程条目换算回源时区后本地时间必须一致。

> **Indico 教训** Indico 自身历史上多次大版本迁移(如 1.x 到 2.x 的 ZODB 到 PostgreSQL)让社区付出惨重代价:一次性、不可重入的脚本一旦中途失败只能从备份重来。yuMeet 迁移器的三条铁律——幂等 upsert、staging 中间层、dry-run 报告先行——都来自这段历史。

## 14.2 通用导入导出

导入导出不依赖迁移器,是产品常规能力,统一入口在管理后台与 REST API(见第 10 章)。所有导入先经 dry-run 产出逐行校验结果,错误行可下载修正后重传;所有含个人数据的导出遵守第 12 章的字段最小化与审计要求。

| 数据 | 导入 | 导出 | 格式与说明 |
| --- | --- | --- | --- |
| 报名名单 | CSV(列映射向导,自动识别常见表头) | CSV / JSON | 自定义字段展开为列;导出列按操作者权限裁剪 |
| 日程 | ICS | ICS(含订阅 URL,见第 5 章) | UID 稳定,重复导入按 UID 更新而非追加 |
| 投稿与评审 | CSV(投稿) | CSV / JSON | 评审数据仅组织者可导,匿名评审不含评审人身份 |
| 完整活动 | `yumeet.export.v1` JSON + media.zip | 同左 | round-trip 保证:导出再导入得到等价活动;跨实例搬迁与备份共用此格式 |
| 开放数据 | — | JSON-LD / RSS / ICS | 只读公开数据,见第 10 章 |

```json
{
  "format": "yumeet.export.v1",
  "yumeet_version": "1.4.0",
  "exported_at": "2026-08-17T08:00:00Z",
  "event": { "slug": "js-conf-2026", "title": "...", "modules": ["registration", "cfp"] },
  "entities": { "registrations": 412, "submissions": 96, "files": 210 },
  "checksums": { "media.zip": "sha256:9f2c..." }
}
```

格式带版本号,导入器向后兼容至少两个 minor 版本;不认识的字段保留在 `extensions` 命名空间原样透传,插件数据(见第 13 章)以插件名为键存于其中。

## 14.3 路线图

路线图按「最小可信产品」切:MVP 的验收不是功能清单打勾,而是第 1 章场景光谱最左端——10 人研讨会——能零文档自助跑通全流程。每个版本都定义明确的退出标准,达不到就不发布。

| 阶段 | 周期 | 功能清单 |
| --- | --- | --- |
| MVP,W1–2 | 第 1–2 周 | monorepo 与 CI 骨架;magic link 认证;核心 Drizzle schema(见第 9 章);docker compose 七容器骨架 |
| MVP,W3–4 | 第 3–4 周 | 三步建会向导;公共活动页(Cupertino 主题,ISR);管理后台框架 /manage |
| MVP,W5–6 | 第 5–6 周 | 表单引擎(8 种基础字段)+ 免费票报名;react-email 确认邮件;状态追踪页 |
| MVP,W7 | 第 7 周 | 只读多轨时间表;ICS 订阅;全站时区渲染 |
| MVP,W8 | 第 8 周 | yumeet CLI(up/backup/doctor);安全基线(见第 12 章);文档与演示活动;性能预算达标(见第 13 章) |
| v1 | MVP 后约 4 个月 | Stripe 支付、优惠码、候补与审批链;CFP + 双盲评审 + 录用流水线;现场签到与 satori 胸牌;REST API + webhooks + API key;模板包与主题切换;Meilisearch 可选驱动;Indico 迁移器 beta;GDPR 自助导出/删除 |
| v2 | v1 后约 6 个月 | Yjs 日程协作编辑;插件市场与三方插件沙箱;SaaS 多租户 GA 与自定义域名;DOI 与引用;规则引擎 GA;企业 SSO 插件(SAML);离线签到 PWA;Typst 会程手册;微信/支付宝社区插件 |

退出标准:MVP——10 人研讨会场景端到端零文档完成,Lighthouse 通过 13.1 预算;v1——一场 500 人规模真实会议完成从建会、收费报名、征稿评审到现场签到的全流程试点;v2——万人抢票压测通过,13.3 的时序在 5000 req/s 峰值下报名接口 p95 低于 800 ms,零超卖。刻意排除在 v2 之前的:房间预订系统、原生移动 App、问卷模块——每一项都有替代路径(外部工具嵌入或插件),不值得推迟核心体验。

## 14.4 开源与商业策略

许可证按「核心防止被闭源托管、边界鼓励生态繁荣」双原则分层:

| 模块 | 许可证 | 理由 |
| --- | --- | --- |
| 核心(apps/*、packages/core) | AGPL-3.0 | 网络服务条款防止云厂商闭源分叉托管;自托管用户不受影响 |
| packages/sdk、插件 API 类型、模板包格式 | MIT | 三方插件与主题不被 AGPL 传染,商业插件可闭源 |
| Cupertino UI 组件库 | MIT | 独立可用,反哺社区与项目知名度 |
| ee/ 目录(SAML SSO、数据驻留、审计导出增强) | 商业许可 | 面向企业付费;构建时可完全剥离,社区版不含任何 ee 代码路径 |

商业模式三条腿:官方 SaaS(同一代码库多租户,见第 2 章)、企业版(ee 功能 + SLA 支持订阅)、插件市场抽成。插件市场规则:所有插件 sigstore 签名分发;首个版本人工审核 + 每版本自动扫描(依赖漏洞、权限声明与实际调用一致性);付费插件与开发者 20/80 分成;manifest 权限清单在安装页原样展示给管理员(见第 13 章)。

治理:贡献采用 DCO 而非 CLA,降低参与门槛(ee 目录贡献例外,需单独协议);任何影响数据模型、API 或插件接口的变更先提 RFC,公开评论期 14 天;初期由核心团队维护,v1 发布后成立 3 到 7 人的 technical steering committee 且必须包含非雇员维护者;发布节奏为每月一个 minor、每年一个 LTS(维护 24 个月)。「yuMeet」名称与标志保留商标,允许「for yuMeet」式的生态命名,禁止让用户误认为官方发行版的用法。

> **设计要点** ee 代码与社区版同仓不同目录,而不是私有仓库:企业功能的接口演进公开可见,社区能验证「开源版没有被故意削弱」,这是 open-core 模式维持信任的最低成本做法。

## 14.5 竞品逐维度对照

四个对照对象覆盖了 yuMeet 的全部竞争面:Indico 是被替代者,ConfTool 与 EasyChair 是学术会议管理的商业与评审侧标杆,Eventbrite 代表商业活动票务的体验上限。

| 维度 | Indico | ConfTool | EasyChair | Eventbrite | yuMeet |
| --- | --- | --- | --- | --- | --- |
| 定位 | 学术活动全流程(CERN 出品) | 学术会议注册与评审 | 投稿评审为主 | 商业活动票务 SaaS | 开源全流程,参与体验优先 |
| 开源与自托管 | MIT 开源,自托管依赖沉重(TeXLive 等) | 闭源,授权托管 | 闭源,仅托管 | 闭源 SaaS | AGPL 开源,一条命令 compose;官方 SaaS 可选 |
| 技术栈 | Python/Flask + Jinja 单体 | PHP | 专有 | 专有 | TypeScript,Next.js + `packages/core` 服务层,Fastify 承担开放 API 与实时(见第 2 章) |
| 注册与票务 | 全面但配置繁重 | 强(学术定价、发票) | 弱 | 强(票务、营销工具) | 表单引擎 + 审批链 + 候补 + Stripe(见第 4 章) |
| 征稿与评审 | 完整(abstract + paper) | 完整 | 最强(超大规模评审) | 无 | 完整,双盲 + 利益冲突内建 |
| 日程编排 | 完整多轨 | 中等 | 弱 | 基本议程展示 | 多轨拖拽 + Yjs 协作 + 草稿/发布版本(见第 5 章) |
| 现场(签到/胸牌) | 有,胸牌走 LaTeX 管线 | 有 | 无 | 强(App 扫码) | 签到 + satori 胸牌 + 会场屏 + SSE 公告 |
| 参会者体验 | 桌面时代 UI,选项过载 | 表单密集 | 功能性 UI | 现代、移动友好 | 内容优先,Cupertino 主题,60 秒报名(见第 3 章) |
| 无摩擦身份 | 需注册账户 | 需注册账户 | 需注册账户 | 可访客购票 | 访客优先,magic link + passkey(见第 6 章) |
| 主题自定义 | 有限的 CSS 覆盖 | logo 级 | 无 | 品牌页有限定制 | 四层模型:开关 → tokens → 模板包 → headless(见第 7 章) |
| API 与 webhooks | 部分 REST + 插件 | 导出接口为主 | 极少 | 完整 API | OpenAPI 3.1 + webhooks + 开放数据(见第 10 章) |
| 隐私与合规 | GDPR 工具后补、有限 | 欧盟托管,较好 | 一般 | 数据商业化用途受争议 | 默认合规:最小化、opt-in、保留期自动清理(见第 12 章) |
| 归档 | 强(CERN 档案传统) | 一般 | 弱 | 活动结束即弱化页面 | 一等公民:永久链接 + DOI + 全量导出 |
| 成本模式 | 免费,自托管人力成本高 | 许可费 | 按会议收费,小会免费 | 票务抽成 + 服务费 | 自托管免费;SaaS 订阅;无票务抽成 |
| 适用规模 | 10 人到万人(学术) | 中大型学术会议 | 评审密集型会议 | 商业活动全规模 | 10 人研讨会到万人大会(见第 1 章) |

对照的结论可以压缩成一句话:在「学术全流程功能」上 yuMeet 对标 Indico 不做减法(除明确的非目标),在「体验、身份、部署」三个维度上以 Eventbrite 与现代 SaaS 为基线做加法,而这三个维度恰恰是 Indico、ConfTool、EasyChair 共同的结构性短板——它们的技术底盘决定了补不上。这也界定了 yuMeet 不打的仗:不与 EasyChair 争夺纯评审工作流的极限规模,不与 Eventbrite 争夺消费级活动的营销分发。竞争策略与第 1 章的产品定位互为印证:赢在交集,而不是在每条单项上称王。
