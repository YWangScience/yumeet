# 第 5 章 · 核心功能 II:日程、现场、归档与通知

本章定义活动生命周期后半段的四组能力:会前的日程编排(5.1)、会中的现场运行(5.2、5.3)、会后的归档(5.4),以及贯穿全程的通知与状态追踪(5.5)。每一节都给出数据结构、协议格式或事件表,与第 9 章的数据模型、第 10 章的 API 定义共用同一套实体命名。

## 5.1 日程编排器

编排器位于 `/manage/{org}/{event}/schedule`,是组织者角色最重的界面。复杂度控制策略是「格子即真相」:横轴为房间(多轨)、纵轴为时间的拖拽网格,每天一个标签页;所有未排入日程的 session 停在左侧「待排区」列表,拖入网格即完成排期,拉伸下边缘即调整时长。时间粒度固定为 5 分钟网格,禁止自由像素定位——这是冲突检测与 ICS 输出可靠性的前提。

### 5.1.1 共享文档结构

拖拽操作不直接写数据库,而是落在一个 Yjs 共享文档上(见 5.1.4)。文档的最小单位是 `ScheduleBlock`,只存排期信息;标题、讲者、摘要等内容字段留在 `session` 实体中(见第 9 章),按 ID 引用,避免协作文档膨胀。

```ts
// 一个 event 对应一个 Y.Doc
interface ScheduleDoc {
  blocks: Y.Map<ScheduleBlock>;   // key: blockId
  meta: Y.Map<string | number>;   // gridStep、dayRange 等
}

interface ScheduleBlock {
  id: string;               // blk_ 前缀,uuidv7
  sessionId: string;        // 指向 session 实体,内容字段见第 9 章
  roomId: string | null;    // null = 停在待排区
  startsAt: string;         // UTC ISO 8601,按浏览者时区渲染
  durationMin: number;      // 5 的倍数
  trackId: string | null;   // 主题轨,用于着色与筛选
  locked: boolean;          // 锁定后拖拽无效,防误碰
}
```

### 5.1.2 冲突检测

冲突检测是一个纯函数,前端在每次拖拽结束时同步执行(千级 block 规模下低于 5ms),服务端在发布前用同一份代码复核——双端共享 `packages/schedule-core`,不允许出现两套判定逻辑。冲突以红色描边加侧栏列表呈现,不用弹窗打断操作;冲突不阻止保存草稿,只阻止发布,组织者可显式覆盖(二次确认并写入审计日志,见第 12 章)。

```ts
type ConflictKind =
  | 'room_overlap'      // 同一房间时间重叠
  | 'speaker_overlap'   // 同一讲者出现在并行的两个 block
  | 'chair_overlap'     // 同一主持人并行冲突
  | 'out_of_hours'      // 超出当天设定的会议时段
  | 'capacity';         // 预计人数超过房间容量(警告级)

// 双端复用的纯函数;capacity 为 warning,其余为 error
function detectConflicts(
  blocks: ScheduleBlock[],
  ctx: EventContext
): Conflict[];
```

### 5.1.3 草稿与发布版本

所有编辑发生在草稿态。点击「发布」后:服务端复核冲突 → 将当前文档物化为一行不可变的 `schedule_version`(JSONB 快照,version 自增)→ 触发公共页 ISR revalidate 与 `schedule.published` 通知(见 5.5.2)。公共活动站永远只读最新已发布版本;回滚不是修改历史,而是把旧快照重新发布为一个新版本。发布确认页展示与上一版的 diff(新增 / 移动 / 删除 / 时长变化四类),让组织者在群发变更通知前看清影响面。

### 5.1.4 Yjs 协作编辑

每个 event 对应一个 Y.Doc,由 apps/api 内的 WebSocket 网关承载(架构位置见第 2 章)。awareness 协议同步协作者的光标位置与选中 block,多名组织者可同时排期,CRDT 保证并发拖拽不丢更新。持久化策略:增量 update 以二进制追加写入 Redis;worker 每 30 秒或每累积 512 次更新合并为 snapshot 写入 Postgres。权限:仅持有 `schedule.edit` 能力(见第 6 章)的会话可换取一次性 WebSocket ticket(60 秒有效)。不支持离线编辑——排期是强协作场景,断线即降级为只读并明示状态。

> **Indico 教训** Indico 的 timetable 编辑器把移动、改时长、换房间都藏进多层表单弹窗,一次调整平均 4 到 6 次点击,且无并发保护,两人同时编辑互相覆盖。yuMeet 用直接操纵(拖拽、拉伸)替代表单,用 CRDT 替代「最后保存者赢」。

## 5.2 现场模式

现场模式是 `/manage/{org}/{event}/onsite` 下的独立子界面,按原则 2 为「站在会场门口的工作人员」做减法:大按钮、高对比、默认深色(适应场馆灯光)、针对平板与手机布局。它包含签到台、胸牌打印、会场屏管理与公告发布四个入口。

### 5.2.1 签到与离线容错

会场网络不可靠是设计前提,签到链路的硬要求是**完全脱网也能验票**。方案分三层:

- **可离线验证的票证。**二维码内容是自包含的签名令牌:活动创建时生成 Ed25519 密钥对,私钥仅 api 持有;签到端联网时预取公钥,此后验签不需要任何网络请求。
- **本地名单快照。**签到端是可安装 PWA(Service Worker 缓存应用壳),开幕前全量拉取名单到 IndexedDB(仅 registrationId、姓名、票种、状态、签到标记五个字段),之后按 `updatedSince` 游标每 60 秒增量同步;断网时以本地快照为准。
- **事件队列与幂等回放。**每次签到写入本地队列,恢复联网后批量上传,服务端按 `opId` 去重。

```ts
// 票面二维码:紧凑签名令牌,离线可验、不含个人信息
const payload = `${registrationId}.${eventId}.${issuedAt}`;
const qr = `PDM1.${base64url(payload)}.${base64url(
  ed25519.sign(payload, eventPrivateKey)
)}`;

// 签到端 IndexedDB 中的事件队列
interface CheckinEvent {
  opId: string;           // uuidv7,同时是服务端幂等键
  registrationId: string;
  stationId: string;      // 签到设备标识
  scannedAt: string;      // 设备时钟,UTC
  synced: boolean;
}
// 联网后 POST /api/v1/events/:id/checkins:batch
// 服务端按 opId 去重;多设备重复签到时 checkedInAt 取最早值,
// 后续提交返回 already_checked_in 而非错误
```

单次扫码流程(目标 1.5 秒内出结果):

1. 摄像头解码 → 校验 `PDM1` 前缀与 Ed25519 签名(本地公钥,毫秒级);签名无效直接红色拒绝。
2. 在 IndexedDB 名单中查 registrationId:状态非 `confirmed` → 红色阻止并显示原因(未支付 / 已取消);记录不存在 → 黄色提示「签名有效但名单未同步」,允许工作人员手动放行并标记。
3. 已有签到标记 → 橙色提示重复,显示首次签到时间与设备,不重复计数。
4. 通过 → 绿色大字显示姓名与票种,写入本地队列;若启用现场打印,同步下发该人的胸牌打印任务。

时钟与冲突处理:`scannedAt` 取设备时钟,服务端另记 `receivedAt`;统计与展示以服务端合并结果为准,设备时钟漂移不影响幂等性(opId 与时间无关)。

> **设计要点** 令牌只含不透明 ID,票据截图外泄不会暴露姓名邮箱。吊销(退款、取消)通过状态下发到名单快照生效,因此存在最长 60 秒(在线)或断网期间的吊销窗口——这是对离线可用性的显式权衡;风控要求高的活动可在设置中切换为「强制在线验票」模式。

### 5.2.2 胸牌生成

胸牌与证书由 satori + resvg 渲染:模板是一个 React 组件(与站点主题解耦,主题机制见第 7 章),satori 输出 SVG,resvg 转 PNG 或合成 PDF。两条生成路径:**会前批量**由 worker 按票种分组渲染、按姓氏排序合并为 A6/A7 版式 PDF 供打印店使用;**现场即时**在签到通过后由 api 单张生成并推给标签打印机。模板变量包括姓名、机构、票种色条、签到 QR、拼音/罗马音辅助行。字体必须内嵌:SF Pro 与 PingFang 不可再分发,默认打包 Inter + Noto Sans SC,组织者可上传自有授权字体。

### 5.2.3 会场屏与实时公告

每个房间有一个免登录展示 URL `/e/{eventId}/rooms/{roomId}/display`(可选加 token),全屏轮显 Now / Next 两个 block 与房间公告,供门口平板或投屏使用。实时通道用 SSE:端点 `GET /api/v1/events/:id/stream`,事件类型 `announcement`(组织者广播,公共页与会场屏顶部横幅)、`schedule`(发布新版本后推送,页面软刷新)、`checkin_stats`(仅组织者面板订阅)。断线重连依赖 `Last-Event-ID` 补发,消息在 Redis 中保留 24 小时。公告可勾选「同时发邮件」,走 5.5 的通知管道。

## 5.3 线上与混合

yuMeet 不自建流媒体——转码与分发交给成熟服务,系统只负责集成、访问控制与出席记录。每个 block(或整个活动)可配置 `virtual` 设置:

- **provider**:`zoom | meet | youtube | vimeo | hls | custom`。嵌入型(YouTube/Vimeo/HLS)在日程详情页内嵌播放器;会议型(Zoom/Meet)显示「加入」按钮。
- **访问级别**:`public | registered | ticket_type`。受限级别的加入链接不直接暴露,统一经 `GET /api/v1/join/:blockId` 校验会话后 302 下发,同时写一条来源为 `online` 的出席记录——线上出席与现场签到进同一张统计表。
- **显示时机**:开始前 N 分钟才显示入口(默认 15),避免公共页提前泄漏会议号。

回放:会后将录像 URL 或上传到 S3 的文件挂到对应 block,可设 `availability: immediately | after_event | 指定日期`;回放页按日程结构聚合,归档后成为资料库的一部分(见 5.4.2)。Zoom/Meet 的 OAuth 集成细节见第 10 章。

## 5.4 归档

按原则 7,归档不是「活动结束后网页碰巧还在」,而是一个有明确语义的生命周期状态:活动存储态仅 `draft → published → archived` 三个,`live` 与 `ended` 是按 `starts_at` / `ends_at` 派生的展示态,不入库。进入 `archived` 后内容冻结、公共站转为纯静态渲染、报名与投稿入口移除,但所有历史页面、资料与链接永久可访问。解冻(unarchive)是显式操作并记审计。

### 5.4.1 永久链接

| URL 形态 | 示例 | 稳定性承诺 |
| --- | --- | --- |
| `/{org}/{event-slug}` | `/cern-alumni/qcd-2026` | 人类可读入口;slug 可改名,历史 slug 永久 301 到新址 |
| `/e/{eventId}` | `/e/evt_01JD8QZ…` | canonical,永不变化,页面 `rel=canonical` 指向它 |
| `/e/{eventId}/s/{sessionId}` | `…/s/ses_01JD9A…` | session 永久页,含时间、讲者、材料、回放 |
| `/e/{eventId}/c/{contribId}` | `…/c/sub_01JDA2…` | 投稿/报告永久页,DOI 落地页指向此处 |
| `/e/{eventId}/f/{fileId}/{filename}` | `…/f/fil_01JDB7…/slides.pdf` | 文件永久链接,经 api 网关下发而非 S3 直链 |

配套约束:所有 ID 为带前缀的不透明 ID 且永不复用;slug 改名写入 `slug_history` 表以支撑 301;文件下载走网关,底层 S3 key 可迁移而不破链,响应头附带 `x-content-sha256`;被删除的资源返回 410 Gone 加说明页,而不是 404——链接失效也要失效得诚实。

### 5.4.2 资料库

文件可挂在 event / session / contribution 三级,每个文件记录 sha256、大小与版本链(新版本是新的 file 行,`supersedes` 指向旧版,旧版仍可经永久链接访问)。讲者上传窗口截止后,组织者一键锁定全部材料。进入归档时 worker 逐文件校验 sha256 并生成 manifest,校验失败的文件在管理后台标红,保证「归档即完整」。

### 5.4.3 引用与 DOI

已归档活动与录用的 contribution 可通过 DataCite 插件注册 DOI(组织级配置凭证,前缀归机构所有),DOI 落地页即 5.4.1 的 contribution 永久页。未启用 DOI 时,每个永久页仍提供引用块(BibTeX 与 APA 两种格式一键复制),并输出 schema.org/Event 与 ScholarlyArticle JSON-LD(见第 10 章)。

### 5.4.4 导出格式

| 格式 | 覆盖范围 | 生成方式 | 典型用途 |
| --- | --- | --- | --- |
| ICS | 日程(全量 / 个人) | api 实时生成 | 日历订阅,见 5.5.4 |
| CSV | 名单、投稿、签到记录、订单 | worker 异步,完成后邮件通知 | 表格分析、财务对账 |
| JSON bundle(`yumeet.event/v1`) | 活动全量结构化数据 + 文件 | worker 打包 zip 存 S3,限时下载链接 | 备份、跨实例迁移、二次开发 |
| PDF 会程手册 | 日程 + 摘要 + 索引 | 容器化 Typst,worker 编译 | 印刷、离线分发 |
| 静态 HTML 快照 | 整个公共活动站 | worker 抓取已发布页面打包 | 机构自存档、断网展示 |
| BibTeX / DataCite XML | 引用元数据 | api 实时生成 | 学术引用、图书馆收录 |

```json
// archive.json —— JSON bundle 顶层结构(yumeet.event/v1)
{
  "bundle": "yumeet.event/v1",
  "exportedAt": "2026-08-17T09:00:00Z",
  "event": { "id": "evt_01JD8QZ", "slug": "qcd-2026", "title": "…" },
  "sessions": ["…"],
  "contributions": ["…"],
  "registrations": ["…(按导出者权限决定是否含个人字段)"],

    { "id": "fil_01JDB7", "sha256": "9f2c…", "path": "files/fil_01JDB7/slides.pdf" }
```

> **Indico 教训** Indico 的会程手册依赖 TeXLive:镜像体积数 GB、模板是散落的 LaTeX 片段、编译失败信息难以定位。yuMeet 用容器化 Typst 替代:编译秒级完成,模板是版本化的单文件代码,错误信息带行号回传到管理后台。

## 5.5 通知与状态追踪

通知系统的第一条规则:**通知由状态迁移驱动,禁止业务代码手工发信**。每一次状态迁移写入 timeline(与审计日志同源,见第 12 章),notification dispatcher 监听迁移事件,查 5.5.2 的事件表决定渠道扇出,再交给 BullMQ 队列执行。这保证追踪页(5.5.3)展示的时间线与实际发出的通知永远一致。

### 5.5.1 关键状态机

注册与投稿的状态全集与迁移表见 9.4,那里是唯一事实源,本节不再重复定义,只定义通知扇出(5.5.2)与追踪页展示(5.5.3)。迁移入口唯一:`transition()` 校验合法性 → 写 timeline → 发领域事件;notification dispatcher 只订阅领域事件,业务代码无权直接调用邮件驱动。

### 5.5.2 通知事件总表

渠道:邮件(react-email 模板与送达追踪见第 4 章)、站内(追踪页与管理后台的收件箱)、SSE(打开中的页面即时横幅)、Webhook(与第 10 章事件表同源)。退订规则:凡影响参会资格、付款与法律义务的**事务性通知不可退订**;提醒类与摘要类可退订,粒度为「类别 × 活动」,每封可退订邮件底部带一键退订链接(`List-Unsubscribe` 头同步声明)。

| `digest.organizer_daily` | 昨日新增报名/投稿/收入汇总(有增量才发) | 邮件 | 可 |

### 5.5.3 进度追踪页

每个 registration 与 submission 都有一个追踪页——报名 `/r/{token}`、投稿 `/s/{token}`(128-bit 不可枚举 token,见 3.4),点开即看、无需登录——这是原则 3 与原则 4 的交点。页面是一条垂直时间线,数据直接来自 timeline 表而非状态推断,每行包含:时间(按浏览者时区)、状态、说明文案、下一步动作按钮(去支付 / 补材料 / 确认候补转正)。顶部固定展示当前状态与预计下一步,例如「审核中——该活动近期审核中位耗时 2 天」,预估值由该活动自身的历史迁移间隔实时计算,没有数据时不显示而不是编一个数。组织者从管理后台打开同一条时间线可见内部备注列,参会者视角自动过滤。

> **Indico 教训** Indico 的注册状态只存在于邮件里:确认信延迟、进垃圾箱,参会者除了写信问组织者别无他法。yuMeet 把邮件降级为「通道之一」:权威状态永远在追踪页上,每封通知邮件底部都带追踪链接,邮件全部丢失也能通过重发 magic link 找回入口;送达追踪与 SPF/DKIM/DMARC 配置指南见 4.4。

### 5.5.4 ICS 订阅

三种日历产物:**个人订阅源**(`webcal://…/api/v1/me/calendar.ics?token=…`,只含我报名的活动与我的场次)、**活动全量订阅源**(公共页「订阅日历」按钮)、**单场 .ics 附件**(随 `registration.confirmed` 邮件发出)。实现要点:

1. UID 稳定:`{blockId}@{host}`,日程调整只改内容不换 UID,客户端原地更新而非产生重复条目;
2. 每次变更 `SEQUENCE` 递增;被取消的场次输出 `STATUS:CANCELLED` 并保留在 feed 中,直接删除会让已订阅客户端残留旧条目;
3. 时间一律 UTC(`Z` 后缀),由客户端按本地时区渲染,与原则 6 一致;
4. 声明 `REFRESH-INTERVAL` 与 `X-PUBLISHED-TTL` 均为 1 小时,服务端配 ETag,未变更返回 304。

```http
GET /api/v1/events/evt_01JD8QZ/calendar.ics HTTP/1.1

HTTP/1.1 200 OK
Content-Type: text/calendar; charset=utf-8
ETag: "sched-v3"

BEGIN:VCALENDAR
VERSION:2.0
PRODID:-//yuMeet//EN
REFRESH-INTERVAL;VALUE=DURATION:PT1H
X-PUBLISHED-TTL:PT1H
BEGIN:VEVENT
UID:blk_01JD9AXQ@yumeet.example.org
SEQUENCE:3
DTSTART:20261012T070000Z
DTEND:20261012T083000Z
SUMMARY:Opening Session
LOCATION:Auditorium A
URL:https://yumeet.example.org/e/evt_01JD8QZ/s/ses_01JD9A
STATUS:CONFIRMED
END:VEVENT
END:VCALENDAR
```
