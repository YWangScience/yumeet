# 第 11 章 · 配置与部署

「运维趋零」原则在本章落地为可执行的产物:四层配置模型与明确的覆盖优先级、一份可直接使用的 docker-compose.yml(七容器)、yumeet CLI 的完整子命令表、从单机到多实例的伸缩路径、备份/恢复/升级流程,以及默认开启的可观测性。目标是:一台干净的 Linux 主机,一个域名,十分钟内跑起生产实例。

## 11.1 零配置哲学与配置分层

yuMeet 的默认值必须能直接进生产:除域名与管理员邮箱外,首次启动不要求任何配置——数据库口令、会话密钥、MinIO 凭证全部由 `yumeet init` 随机生成写入 `.env`。「可配置」不等于「必须配置」:每个配置项都有经过论证的默认值,配置面暴露给用户的顺序遵循渐进披露(见第 1 章)。

配置分四层,**后者覆盖前者**;凡被环境变量或配置文件固定的键,管理后台对应表单项变为只读并标注「由 ENV 锁定」——杜绝「UI 改了不生效」这类排障黑洞:

| 层 | 载体 | 适用内容 | 生效方式 |
| --- | --- | --- | --- |
| 1 内置默认 | 代码内 Zod schema 的 `.default()` | 一切有合理通值的项(时区渲染、分页大小、重试策略) | 随版本发布 |
| 2 管理后台 UI | Postgres `settings` 表(组织/实例两级) | 业务偏好:品牌、邮件发件人、注册默认项、主题 | 保存即热生效 |
| 3 环境变量 | `.env` / 容器编排注入 | 连接串、密钥与实例形态:`DATABASE_URL`、`REDIS_URL`、`S3_*`、`SMTP_URL`、`SESSION_SECRET`、`YUMEET_MODE` | 重启进程生效 |
| 4 配置文件 | `yumeet.yaml`(可选,挂载进容器) | GitOps/IaC 场景:整实例声明式钉死,含插件启停 | 重启进程生效,校验失败拒绝启动 |

全部配置在启动时经同一份 Zod schema 校验,任何非法值 fail-fast 并打印键名、收到的值与期望类型——而不是带着错误配置静默运行。`yumeet config list` 可打印每个键的最终值与来源层,这是排查配置问题的第一入口。

> **设计要点**:第 2、3、4 层的分工不是按「高级程度」而是按**变更主体**划分——业务人员改的进 UI 层,运维改的进 ENV 层,平台工程用代码管的进文件层。三者互不越界,才能既满足「简单用」又满足「高端自定义」。

## 11.2 一条命令部署

部署前提只有两个:一台可公网访问的主机(建议 2 vCPU / 4 GB 起),一条指向它的 DNS A/AAAA 记录。流程:

1. `curl -fsSL https://get.yumeet.dev | sh` 安装 yumeet CLI(或直接 clone 发布仓库)。
2. `yumeet init --domain events.example.org --email ops@example.org`:交互确认后生成 `.env`(随机密钥)、`Caddyfile`、`docker-compose.yml`。
3. `yumeet up`:拉取镜像、启动七容器、等待健康检查、执行数据库迁移。Caddy 通过 ACME 自动签发并续期 TLS 证书,无任何证书配置。
4. 浏览器访问域名,完成首次运行向导(创建管理员,passkey 或 magic link,见第 6 章)。

生成的 compose 文件如下,即产品所述的七容器:caddy、web、api、worker、postgres、redis、minio:

```yaml
name: yumeet

x-app-env: &app-env
  NODE_ENV: production
  YUMEET_DOMAIN: ${YUMEET_DOMAIN}
  YUMEET_MODE: ${YUMEET_MODE:-single}
  DATABASE_URL: postgres://yumeet:${POSTGRES_PASSWORD}@postgres:5432/yumeet
  REDIS_URL: redis://redis:6379
  S3_ENDPOINT: http://minio:9000
  S3_BUCKET: yumeet
  S3_ACCESS_KEY: ${MINIO_ROOT_USER}
  S3_SECRET_KEY: ${MINIO_ROOT_PASSWORD}
  SESSION_SECRET: ${SESSION_SECRET}
  SMTP_URL: ${SMTP_URL}

services:
  caddy:
    image: caddy:2-alpine
    restart: unless-stopped
    ports:
      - "80:80"
      - "443:443"
      - "443:443/udp"   # HTTP/3
    environment:
      YUMEET_DOMAIN: ${YUMEET_DOMAIN}
      ACME_EMAIL: ${ACME_EMAIL}
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile:ro
      - caddy_data:/data
      - caddy_config:/config
    depends_on:
      - web
      - api

  web:
    image: ghcr.io/yumeet-events/web:${YUMEET_VERSION:-latest}
    restart: unless-stopped
    environment:
      <<: *app-env
      API_ORIGIN: http://api:4000
    depends_on:
      api:
        condition: service_healthy
    healthcheck:
      test: ["CMD", "wget", "-qO-", "http://127.0.0.1:3000/healthz"]
      interval: 15s
      timeout: 5s
      retries: 5

  api:
    image: ghcr.io/yumeet-events/api:${YUMEET_VERSION:-latest}
    restart: unless-stopped
    environment:
      <<: *app-env
    depends_on:
      postgres:
        condition: service_healthy
      redis:
        condition: service_healthy
      minio:
        condition: service_healthy
    healthcheck:
      test: ["CMD", "wget", "-qO-", "http://127.0.0.1:4000/healthz"]
      interval: 15s
      timeout: 5s
      retries: 5

  worker:
    image: ghcr.io/yumeet-events/worker:${YUMEET_VERSION:-latest}
    restart: unless-stopped
    environment:
      <<: *app-env
    depends_on:
      postgres:
        condition: service_healthy
      redis:
        condition: service_healthy
      minio:
        condition: service_healthy
    healthcheck:
      test: ["CMD", "node", "dist/healthcheck.js"]  # 检查 BullMQ 连接与队列心跳
      interval: 30s
      timeout: 10s
      retries: 3

  postgres:
    image: postgres:17-alpine
    restart: unless-stopped
    environment:
      POSTGRES_USER: yumeet
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: yumeet
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U yumeet -d yumeet"]
      interval: 10s
      timeout: 5s
      retries: 10

  redis:
    image: redis:7-alpine
    restart: unless-stopped
    command: redis-server --appendonly yes
    volumes:
      - redisdata:/data
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 10s
      timeout: 3s
      retries: 10

  minio:
    image: minio/minio:RELEASE.2025-04-22T22-12-26Z
    restart: unless-stopped
    command: server /data --console-address ":9001"
    environment:
      MINIO_ROOT_USER: ${MINIO_ROOT_USER}
      MINIO_ROOT_PASSWORD: ${MINIO_ROOT_PASSWORD}
    volumes:
      - miniodata:/data
    healthcheck:
      test: ["CMD", "curl", "-f", "http://127.0.0.1:9000/minio/health/live"]
      interval: 15s
      timeout: 5s
      retries: 5

volumes:
  caddy_data:
  caddy_config:
  pgdata:
  redisdata:
  miniodata:
```

Caddy 承担 TLS 终结、HTTP/3、压缩与路由分发,整个反向代理配置只有一个文件:

```yaml
# Caddyfile
{
  email {$ACME_EMAIL}
}

{$YUMEET_DOMAIN} {
  encode zstd gzip

  handle /api/v1/* {
    reverse_proxy api:4000
  }
  handle /storage/* {
    reverse_proxy minio:9000
  }
  handle {
    reverse_proxy web:3000
  }
}
```

> **对照 Indico**:Indico 自托管需要 Python 运行时、Celery、TeXLive(数 GB)、外置 LDAP 等一长串依赖,官方文档的安装章节按操作系统分发维护多套步骤。yuMeet 把全部依赖封进七个容器与一个 `.env`,胸牌/证书用 satori + resvg、会程手册用容器化 Typst(见第 5 章),彻底移除 TeXLive 这一最重的运维负担。

## 11.3 yumeet CLI

CLI 是 compose 之上的薄封装加运维工具箱,所有子命令幂等、可脚本化(`--json` 输出),不引入 compose 之外的状态:

| 子命令 | 作用 | 示例 |
| --- | --- | --- |
| `init` | 生成 `.env`、`Caddyfile`、`docker-compose.yml`,随机生成全部密钥 | `yumeet init --domain events.example.org --email ops@example.org` |
| `up` | 拉取镜像、启动七容器、等健康检查、跑迁移 | `yumeet up` |
| `down` | 停止全部容器,保留数据卷 | `yumeet down` |
| `status` | 各容器健康状态、版本、磁盘与队列积压概览 | `yumeet status --json` |
| `logs` | 聚合结构化日志,按服务过滤、跟随 | `yumeet logs api -f --since 1h` |
| `doctor` | 体检:DNS 解析、80/443 可达、磁盘余量、证书有效期、SMTP 连通、备份新鲜度、迁移一致性,输出逐项通过/失败与修复建议;`--audit-verify` 全链重算审计哈希链(见 12.5) | `yumeet doctor` |
| `backup` | 全量备份(pg_dump + MinIO 数据 + `.env`)为单一归档,可推送到外部 S3 | `yumeet backup --to s3://backups/yumeet/` |
| `restore` | 从备份归档恢复到当前或新主机 | `yumeet restore yumeet-2026-08-17T0300.tar.zst` |
| `upgrade` | 自动备份 → 拉新镜像 → 迁移 → 按依赖顺序重启 → doctor 验证 | `yumeet upgrade --to 1.4.2` |
| `rollback` | 镜像回退到上一版本(数据库不回滚,见 11.5) | `yumeet rollback` |
| `config` | 读写 ENV 层配置并打印每个键的生效来源 | `yumeet config set SMTP_URL=smtp://key@smtp.eu.example.com:587` |
| `admin` | 管理员账户兜底操作(创建、重发登录链接、解锁) | `yumeet admin create --email ops@example.org` |
| `migrate` | 从 Indico 或通用格式导入既有数据(见 14.1) | `yumeet migrate --from indico ./indico-export/` |
| `search` | `reindex`:全量重建 Meilisearch 索引(见 13.6) | `yumeet search reindex` |
| `theme` | `add`/`remove`:安装 L2 模板包(见 7.3) | `yumeet theme add @yumeet/theme-conference` |

## 11.4 伸缩路径

伸缩是逐步替换,不是重构:web/api/worker 三个应用容器从第一天起就是无状态的(会话在 httpOnly cookie + 服务端存储,上传直达 S3,任务在 Redis 队列),因此每一阶段只改连接串或副本数,不改代码。

| 阶段 | 形态 | 触发信号 | 需要的变更 |
| --- | --- | --- | --- |
| 0 | 单机 compose(本章默认) | ——绝大多数部署终身停留在此阶段;公共页全走 ISR,万人大会的读流量不构成压力 | 无 |
| 1 | 外接托管依赖 | Postgres CPU 持续高于 60%,或需要跨可用区容灾/托管备份 | 将 `DATABASE_URL`、`REDIS_URL`、`S3_*` 指向 RDS/ElastiCache/S3 等托管服务,`yumeet up --without postgres,redis,minio` |
| 2 | 多实例水平扩展 | 报名写路径 p95 超预算(见第 13 章),或单机资源到顶 | web/api/worker 各自多副本置于负载均衡后;SSE 广播经 Redis pub/sub fan-out;Yjs WebSocket 开 sticky session;公共站点前置 CDN |
| 3 | SaaS 多租户 | 以平台形式运营多组织 | 同一镜像,`YUMEET_MODE=saas`,租户模型见第 2 章与第 6 章 |

## 11.5 备份、恢复与升级

**备份**默认开启:worker 每日 03:00(实例时区)执行,归档包含四部分——`pg_dump -Fc` 数据库快照、MinIO bucket 增量同步、`.env` 与 `Caddyfile`、记录版本号与各部分校验和的 `manifest.json`。保留策略为 GFS:近 7 日每日一份、近 4 周每周一份、近 12 月每月一份;`yumeet doctor` 会在最近备份超过 26 小时时报警。备份必须推到异机(`--to s3://` 指向外部对象存储),本机备份只防误删不防主机故障。

**恢复**(同机重建或迁移到新主机同一流程):

1. 新主机安装 CLI,取回备份归档。
2. `yumeet restore `:校验 manifest 校验和,展开 `.env` 与 Caddyfile。
3. CLI 启动 postgres/redis/minio,导入 `pg_dump` 快照与对象数据。
4. 按归档中记录的版本号拉起 web/api/worker——恢复到备份时刻的代码版本,而非最新版。
5. DNS 切换到新主机,Caddy 自动重签证书。
6. `yumeet doctor` 全绿后,再按需 `yumeet upgrade`。

**升级**:`yumeet upgrade` 的每一步失败即中止并保留现场:

1. 自动执行一次备份(可用 `--skip-backup` 跳过,不建议)。
2. 拉取目标版本镜像;跨大版本时强制逐个次版本升级,拒绝跳版。
3. 以一次性容器运行 Drizzle 迁移。迁移只前进不后退,破坏性变更遵循 expand-and-contract:版本 N 新增列/表并双写,版本 N+1 才删除旧结构——保证 N 与 N+1 的代码可同时安全运行于同一 schema。
4. 按 worker → api → web 顺序滚动重启,healthcheck 通过才继续下一个。
5. 自动跑 `doctor`,失败则提示 `yumeet rollback`。

**回滚语义**要向运维者明确交代:`rollback` 只回退镜像。因为 expand-and-contract 保证了向后一格兼容,回退一个版本无需动数据库;要回退数据(如误删除),唯一正确路径是 `restore` 到备份点。CLI 在 rollback 跨越超过一个版本时直接拒绝并指引走 restore。

## 11.6 可观测性

三个应用容器统一输出 pino 结构化 JSON 日志到 stdout,由 Docker 日志驱动收集;每条请求日志携带 `req_id`(即 10.2 错误响应中的 `request_id`)、组织/活动上下文与耗时,个人数据(邮箱、姓名)一律不入日志(见第 12 章):

```json
{"level":"info","time":"2026-08-17T09:30:12.481Z","service":"api","req_id":"req_01J5R0AHXDN4QW","org_id":"org_01J2M4K8Q0","route":"POST /api/v1/events/:id/registrations","status":201,"duration_ms":38,"msg":"request completed"}
```

**OpenTelemetry** 默认内置、按需开启:设置 `OTEL_EXPORTER_OTLP_ENDPOINT` 即向任意 OTLP 后端(Grafana、Jaeger、Datadog 等)导出 trace 与 metrics,未设置则零开销。自动埋点覆盖 Fastify 路由、Postgres 查询、Redis、BullMQ 与出站 fetch;trace context 随任务元数据穿透队列,一次报名从 web 表单提交到确认邮件发出是同一条 trace。

**健康检查端点**:`/healthz` 为 liveness(进程存活即 200,不查依赖,避免依赖抖动引发重启风暴);`/readyz` 为 readiness,逐项探测依赖并给出延迟,负载均衡与 `yumeet status` 都消费它:

```json
{
  "status": "ok",
  "version": "1.4.2",
  "checks": {
    "postgres": { "status": "ok", "latency_ms": 2 },
    "redis": { "status": "ok", "latency_ms": 1 },
    "s3": { "status": "ok", "latency_ms": 9 },
    "queue": { "status": "ok", "waiting": 4 }
  }
}
```

关键指标与建议告警阈值(经 OTLP 导出,或由 `yumeet status --json` 拉取):

| 指标 | 类型 | 建议告警阈值 |
| --- | --- | --- |
| `http_request_duration_ms`(按路由) | histogram | 写路径 p95 超过第 13 章性能预算 |
| `queue_waiting_jobs`(按队列) | gauge | 邮件队列持续 5 分钟大于 100 |
| `email_bounce_rate` | ratio | 24h 内高于 2%(直接威胁「确认邮件不进垃圾箱」的产品承诺) |
| `webhook_failure_rate`(按 endpoint) | ratio | 1h 内高于 50% |
| `disk_used_percent` | gauge | 高于 80%(pgdata 与 miniodata 分别统计) |
| `backup_age_hours` | gauge | 大于 26 |
