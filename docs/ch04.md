# 第 4 章 · 核心功能 I:活动创建、注册与征稿

本章定义活动生命周期前半段的三大功能:活动创建向导、注册与票务引擎、征稿与评审流水线,以及贯穿三者的邮件模板系统。所有配置遵循渐进披露:默认值可直接上线,高级项收进折叠面板,任何模块都不要求组织者理解未开启的功能。

## 4.1 活动创建向导与渐进披露

建会向导固定三步,必填字段总数不超过 6 个,目标 5 分钟内发布(验收旅程见 3.3 旅程 B):

1. **基本信息**:名称、起止日期、时区、地点类型(线下 / 线上 / 混合)。slug 由名称实时生成并查重。
2. **外观**:选择模板包(默认 Cupertino),可选上传 logo 与主色;右侧实时预览。整步可跳过。
3. **创建**:生成 draft 状态的活动、默认单轨日程与默认注册表单(姓名 + 邮箱),进入 dashboard。

向导之外的一切功能都是**模块**,在 dashboard 按需开启。开启即以默认配置生效,同时在公共站与管理导航出现对应入口;关闭则彻底消失,而不是灰置。

| 模块 | 默认 | 开启后出现 | 依赖 |
| --- | --- | --- | --- |
| 注册 | 开 | 公共站 /register;管理端表单、票种、名单 | 无 |
| 征稿 | 关 | 公共站 /cfp;管理端投稿、评审、录用 | 无 |
| 日程 | 开(单轨) | 公共站 /schedule;管理端编排器(见 5.1) | 无 |
| 支付 | 关 | 票种可定价、订单与退款、发票字段 | Stripe 插件已连接 |
| 签到与胸牌 | 关 | 签到 PWA、胸牌模板、打印队列(见 5.2) | 注册 |
| 直播与回放 | 关 | session 级直播嵌入(见 5.3) | 日程 |

每个模块的设置页遵循同一版式:顶部 5 至 7 个常用项,底部一个「高级」折叠区收纳其余全部选项。三层披露依次是:向导默认值 → 模块常用设置 → 高级设置。任何一层都必须是**可发布的完整状态**,不存在「必须进高级页才能用」的路径。

> **对照 Indico** Indico 建会前先要理解 category 树,建会后面对上百个平铺设置项与十余个侧边栏条目。yuMeet 的对照做法是:零个前置概念(组织即命名空间),设置项按「是否 80% 活动都会改」划入常用区,其余一律折叠并可搜索(⌘K,见 8.6)。

## 4.2 注册与票务

### 表单引擎

注册表单由有序的分节(section)与字段(field)组成。姓名、邮箱为核心字段,固定存在且存入关系列;自定义字段的值存 JSONB,由字段定义动态生成 Zod schema 在提交时校验(存储与校验机制见 9.3)。字段类型如下:

| 类型 key | 控件 | 存储值 | 校验与选项 |
| --- | --- | --- | --- |
| `short_text` | 单行文本 | string | minLength / maxLength / pattern |
| `long_text` | 多行文本 | string | maxLength,可显示剩余字数 |
| `email` | 邮箱输入 | string | RFC 5322 语法;可选 MX 记录检查 |
| `phone` | 电话(带国家码) | string(E.164) | libphonenumber 校验 |
| `number` | 数字 | number | min / max / step / 整数开关 |
| `date` | 日期选择器 | string(ISO 8601 日期) | min / max 日期 |
| `select` | 下拉单选 | string(option key) | 选项表;选项可停用不可删除 |
| `radio` | 单选组 | string(option key) | 同上,适合 ≤ 5 项 |
| `checkbox_group` | 多选组 | string[] | minSelected / maxSelected |
| `boolean` | 开关 / 勾选 | boolean | consent 变体绑定法律文本及其版本号,勾选时间入审计日志 |
| `country` | 国家 / 地区选择 | string(ISO 3166-1 alpha-2) | 本地化显示名 |
| `url` | 链接 | string | http/https scheme 白名单 |
| `file` | 文件上传 | fileId 引用 | MIME / 大小白名单;S3 直传;病毒扫描(见 12.2) |
| `affiliation` | 机构输入 | string + 可选 ROR id | ROR 自动补全,允许自由文本 |
| `capacity_option` | 带余量的选项(晚宴、工作坊) | string(option key) | 选项级库存,实时余量显示,可挂候补 |

### 条件逻辑

规则以声明式 JSON 存于表单定义,前端即时求值控制渲染,后端提交时用**同一份规则**重新生成动态 Zod schema 复核(前端不可信)。规则在保存表单时做拓扑排序,存在循环依赖即拒绝保存。示例:学生票要求上传学生证,素食或过敏者追问细节:

```json
{
  "rules": [
    {
      "id": "rule_student_proof",
      "when": {
        "all": [
          { "field": "ticket_type", "op": "eq", "value": "student" }
        ]
      },
      "then": [
        { "action": "show", "field": "student_id_card" },
        { "action": "require", "field": "student_id_card" }
      ]
    },
    {
      "id": "rule_dietary_detail",
      "when": {
        "any": [
          { "field": "dietary", "op": "in", "value": ["vegetarian", "other"] },
          { "field": "has_allergy", "op": "eq", "value": true }
        ]
      },
      "then": [
        { "action": "show", "field": "dietary_note" }
      ]
    }
  ]
}
```

操作符集合:`eq / neq / in / not_in / gt / gte / lt / lte / contains / is_empty`;动作集合:`show / hide / require / set_options`(按条件裁剪选项列表)。被隐藏字段的已填值在提交时丢弃并不参与校验。

### 审批链

每个票种可配置三种审批模式:自动通过、人工审批、**条件审批**(规则命中即自动通过,未命中转人工,例如「邮箱域在成员单位白名单内 → 自动通过」)。人工审批支持多级:按序定义 stage,每个 stage 指定审批人集合与 SLA(如 48 小时),超时向审批人发提醒并在 dashboard 置顶。每次状态迁移写入 registration 的 timeline,参会者的追踪页同步可见(见 5.5);完整状态机见 9.4。

> **对照 Indico** Indico 的审批对申请者是黑箱:提交后只能等邮件。yuMeet 要求每个 pending 状态都有对外可见的解释文案与预计时长,状态页像物流追踪一样逐站展示。

### 候补、限额与库存

限额分三级:活动总量、票种、`capacity_option` 选项级。售罄票种自动转入候补(可关闭),候补按 FIFO 排队,也允许组织者定向放行。名额释放后系统向队首发送限时确认链接(默认 24 小时),过期自动顺延下一位。防超售由两层保证:Redis 原子预占(下单时,10 分钟 TTL)加 PostgreSQL 检查约束(落库时),高并发时序见 13.3。

### 支付、优惠码与团体报名

付费票走 order 实体:一个 order 聚合同一付款人的多张票,记录币种、税率、发票抬头。支付经 Stripe 插件走 Checkout Session:api 创建 Checkout Session(透传幂等键),worker 消费 `checkout.session.completed` webhook 幂等推进订单状态:`pending → paid → refunded / partially_refunded`;退款策略按票种配置(全额截止日、阶梯比例)。优惠码三类:`percentage`(折扣率)、`fixed`(定额减免)、`unlock`(解锁隐藏票种,如内部票);限制维度包括总次数、单邮箱一次、邮箱域、时间窗;支持批量生成一次性码并导出 CSV。团体报名:一人代付 N 张后,系统生成 N 个不可枚举的认领链接,被邀者各自填写个人信息成为独立 registration;未认领的票在管理端可随时回收退款。

## 4.3 征稿与评审

### CFP 配置

征稿按 track 组织;每个 track 可定义多种投稿类型(talk / poster / workshop),每种类型绑定一份表单——复用 4.2 的表单引擎,常用字段:标题、摘要(字数上限)、关键词(受控词表可选)、作者列表(标注报告人)、文件。截止时间分四档:提交、修改、评审、通知,存 UTC、按浏览者时区渲染,截止瞬间由服务器时钟裁决并允许配置宽限期(默认 0)。

### 双盲与利益冲突

track 级开关开启双盲后:评审视图隐藏作者与机构字段;上传文件由 worker 重写文件名为 `submission-{sid}.pdf` 并剥离 PDF 元数据(Info 字典与 XMP);投稿页提醒作者自查正文署名。利益冲突两路检测:作者与审稿人**机构相同**(ROR id 或规范化机构名匹配)或**邮箱域相同**时系统自动标记,禁止分配,chair 可逐条覆核;审稿人另可手动声明。同一 track 内既投稿又评审者,其稿件对本人完全不可见(队列、讨论、统计均排除)。

### 评分维度

维度可按 track 自定义,默认四维:

| 维度 | 量表 | 权重 | 说明 |
| --- | --- | --- | --- |
| novelty 新颖性 | 1–5 | 0.3 | 相对领域现状的增量 |
| relevance 相关性 | 1–5 | 0.3 | 与活动主题及 track 的契合 |
| clarity 清晰度 | 1–5 | 0.2 | 摘要与材料的表达质量 |
| recommendation 总评 | −3…+3 | 0.2 | strong reject 至 strong accept |
| confidence 置信度 | 1–5 | 不计分 | 可选作为聚合时的二次权重 |

总分为加权平均;排序视图同时展示均值、方差与评审完成度,方差过高的稿件自动打上「意见分歧」标签供 chair 优先讨论。

### 评审讨论与录用流水线

每篇稿件有一条委员会内部讨论线程,讨论发生在 `under_review` 态内而非独立状态,审稿人**提交自己的评审后**才可见他人评审与讨论(防锚定);可选 rebuttal 阶段向作者开放脱敏意见并限时回复。录用流水线状态全集(唯一事实源见 9.4):`draft / submitted / under_review / changes_requested / accepted / confirmed / scheduled / rejected / withdrawn`;waitlist 不是状态,而是录用决定上的标记;`accepted` 后经作者确认进入 `confirmed`,自动授予 speaker 角色并把该报告投入日程编排器的未排程池(见 5.1),排入日程后转 `scheduled`。决策支持批量操作:勾选多篇 → 选决定 → 选邮件模板 → 预览合并变量 → 定时发送;通知邮件未发出前,决定对作者不可见。

## 4.4 邮件与消息模板

所有邮件用 react-email 编写为 TSX 组件,随主题包可整体覆盖(见第 7 章);文案经 ICU MessageFormat 本地化,变量在渲染时注入。示例模板:

```ts
import { Html, Container, Heading, Text, Button } from '@react-email/components';
import type { RegistrationConfirmedProps } from './types';

export default function RegistrationConfirmed(
  { attendee, event, trackingUrl }: RegistrationConfirmedProps,
) {
  return (
    <Html lang={event.locale}>
      <Container>
        <Heading>{event.name}</Heading>
        <Text>
          {attendee.firstName},你的报名已确认。开始时间:
          {formatInTz(event.startsAt, attendee.timezone)}
        </Text>
        <Button href={trackingUrl}>查看我的票</Button>
      </Container>
    </Html>
  );
}
```

合并变量按命名空间组织:`attendee.*`(firstName、lastName、email)、`event.*`(name、startsAt、venue、url)、`registration.*`(status、ticketType、qrUrl)、`submission.*`(title、decision)、`org.*`(name、logoUrl)。日期变量强制经 `formatInTz` 按收件人时区渲染,模板中直接内插原始 Date 会在 lint 阶段报错。系统事件邮件全部有默认模板:注册确认、审批结果、候补放行、支付收据、投稿确认、评审邀请、录用通知、日程变更、活动前提醒(T-7 / T-1 可配)。

送达追踪:每封邮件记录状态链 `queued → sent → delivered → opened → bounced / complained`(opened 依赖像素,受隐私代理影响仅作参考);硬退信与投诉地址自动进入抑制表,群发前预检并提示。交易邮件与营销类群发走不同发送流与子域;发送域未完成 SPF / DKIM / DMARC 验证时,系统允许交易邮件但禁用群发,后台提供逐步验证向导与 DNS 记录复制按钮。每封邮件带 `List-Unsubscribe`(one-click)头;退订只作用于营销类,不影响交易通知。

> **设计要点** 邮件是状态机的投影,不是独立功能:任何状态迁移只在事务提交后经 BullMQ 出站,同一迁移使用幂等键去重,保证「参会者看到的追踪页」与「收到的邮件」永远一致。
