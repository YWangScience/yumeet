# 第 13 章 · 性能、可靠性与扩展系统

本章把「快」与「不坏」从口号变成可执行的工程约束:给出以 CI 门禁强制执行的性能预算,分层缓存与失效规则,抢票场景下从幂等键到超时释放的完整扣减时序,以及插件、规则引擎、搜索三套扩展机制的接口定义。目标是任何一个数字、任何一个 hook 都能直接落到代码评审的检查项里。

## 13.1 性能预算

性能预算不是目标值而是**硬约束**:预算写进仓库根目录的 `perf-budget.json`,由 CI 中的 Lighthouse CI 与 `size-limit` 校验,超标即阻断合并——与类型错误同级,不允许「先合了再优化」。公共活动页与管理后台分别设预算,因为二者受众与加载模式不同(见第 2 章的读写路径分离):公共页面向匿名参会者,必须在中端手机的 4G 网络下达标;管理后台面向组织者,允许更大的初始负载但交互延迟标准不放松。

| 指标 | 公共活动页(p75,移动端) | 管理后台(p75,桌面) | 测量方式 | 超标处理 |
| --- | --- | --- | --- | --- |
| LCP | ≤ 1.8 s | ≤ 2.5 s | Lighthouse CI + RUM | CI 阻断 / 线上告警 |
| INP | ≤ 200 ms | ≤ 200 ms | RUM(web-vitals 上报) | 线上告警 |
| CLS | ≤ 0.1 | ≤ 0.1 | Lighthouse CI + RUM | CI 阻断 |
| TTFB(CDN 命中) | ≤ 200 ms | — | 合成监控 | 线上告警 |
| TTFB(回源) | ≤ 600 ms | ≤ 600 ms | 合成监控 | 线上告警 |
| 首屏 JS(gzip) | ≤ 90 KB | ≤ 300 KB | size-limit(CI) | CI 阻断 |
| HTML 文档大小 | ≤ 60 KB | — | size-limit(CI) | CI 阻断 |
| Hero 图片 | ≤ 180 KB(AVIF/WebP) | — | 上传管线自动压缩 | 自动转码 |
| API 读请求 p95 | ≤ 150 ms | OpenTelemetry(见第 11 章) | 线上告警 |  |
| API 写请求 p95 | ≤ 400 ms | OpenTelemetry | 线上告警 |  |
| SSE 公告端到端延迟 | ≤ 2 s | 合成探针 | 线上告警 |  |

RUM 通过 `web-vitals` 库以 10% 采样率上报到 OpenTelemetry 管线,按活动、页面类型、国家维度聚合。公共页 90 KB JS 预算之所以能守住,依赖 RSC 架构:日程、讲者列表等纯展示内容不下发组件代码,只有报名表单、时区切换器等少量交互岛屿是 client component。

## 13.2 缓存与静态化

缓存分五层,每层只解决一类问题,失效统一走**基于 tag 的主动失效**而不是猜 TTL。tag 命名规则:`event:{id}`、`org:{id}`、`schedule:{eventId}`、`speakers:{eventId}`,由写路径在事务提交后统一触发(公共页读路径见第 2 章)。

| 层 | 缓存内容 | 兜底 TTL | 失效方式 |
| --- | --- | --- | --- |
| 浏览器 | 带 hash 的静态资源(JS/CSS/图片) | 1 年,`immutable` | 文件名 hash 变化 |
| CDN / Caddy 边缘 | 公共页 HTML、图片 | 60 s + `stale-while-revalidate=86400` | 回源感知 ISR 重新生成 |
| Next.js ISR(Full Route Cache) | 已发布活动的公共页整页 | 不过期 | `revalidateTag()` |
| Redis | API 层聚合读(日程 JSON、统计数) | 300 s | 写路径按 tag 前缀删除 |
| REST 响应 | 对外 API 的 GET 资源 | — | ETag + `If-None-Match` 304 |

失效的触发点收敛在少数几个领域动作上:活动发布/更新公共信息、日程版本发布、讲者资料变更、主题切换。每个动作对应固定的 tag 集合,写在领域服务里而不是散落在 route handler 中:

```ts
// packages/core/src/events/publish.ts
export async function publishEvent(eventId: string) {
  await db.transaction(async (tx) => { /* 状态迁移、审计,见第 9 章 */ });
  // 事务提交后统一失效,失败进 BullMQ 重试队列,保证最终一致
  await invalidate([`event:${eventId}`, `org:${event.orgId}`, `schedule:${eventId}`]);
}
```

ETag 由资源的 `updated_at` 与 id 计算弱校验值,列表接口用集合最大 `updated_at` 加行数。归档活动(见第 5 章)在归档时整体静态导出,CDN TTL 提升到 7 天——归档内容不可变是「归档是一等公民」原则的性能红利。

## 13.3 高并发报名(抢票场景)

热门活动开票瞬间的流量特征是:秒级尖峰、绝大多数请求注定失败(库存远小于需求)、用户会疯狂重试。设计原则只有一条:**Postgres 是唯一事实来源(落账),Redis 只做准入控制(预扣),排队在最外层削峰**。Redis 预扣的作用是让注定失败的请求在 1 ms 内被拒绝,而不是压到数据库的行锁上;即使 Redis 数据全丢,正确性仍由 Postgres 的原子条件更新兜底,丢的只是吞吐。

完整时序如下(前置条件:活动发布时 worker 已把每种票的可售余量写入 Redis `stock:{ticketId}`,值为 Postgres 口径的 `quantity_total - quantity_sold - active_holds`):

1. **排队削峰(surge 模式,自动开启)**:API 检测到某活动近 10 秒报名请求速率超过阈值(默认 50 req/s)时进入 surge 模式,新会话被写入 Redis 有序集合 `queue:{eventId}`(score 为进入时间戳),前端通过 SSE 收到实时位次——排队页本身就是第 5 章「像查快递」状态透明原则的应用。轮到时签发 admission JWT(有效期 5 分钟),此后所有报名请求必须携带,否则 403。
2. **生成幂等键**:客户端进入报名表单页时生成 `Idempotency-Key: uuidv7()`,存入 sessionStorage;提交与所有自动重试都携带同一个值。用户狂点提交按钮、网络超时重发,都不会产生第二笔预扣。
3. **幂等检查**:`POST /api/v1/events/{id}/registrations` 到达后,API 先执行 `SET idem:{key} "processing" NX EX 900`。键已存在且值为 `processing` → 返回 409,客户端按 Retry-After 轮询;键值为已完成响应的快照 → 直接原样重放,整个后续流程不再执行。
4. **Redis 预扣**:执行下方 Lua 脚本。库存不足返回 0,API 响应 `sold_out` 并附候补(waitlist)入口;足够则原子地 `DECRBY` 库存并写入 `hold:{holdId}`(值为数量,TTL 600 秒)。Lua 在 Redis 内单线程执行,「检查-扣减」之间不存在竞态窗口。
5. **Postgres 落账(第一段:预留)**:单事务写入 `registration`(状态 `awaiting_payment`;免费票直接按第 8 步逻辑置 `confirmed` 并跳过 6–7)、`order`(含 `hold_expires_at`)、`inventory_ledger` 一条 `reserve` 流水。事务提交后把 `idem:{key}` 更新为响应快照,返回 201 与支付参数。
6. **注册超时定时器**:同时投递 BullMQ 延迟任务 `release-hold`(delay 600 s,jobId = holdId)作为超时释放的主定时器;Redis key 过期的 keyspace notification 只作兜底,因为它不保证投递。
7. **支付**:API 创建 Stripe Checkout Session 时透传同一幂等键(Stripe 侧幂等,重复创建返回同一 Session),客户端跳转到返回的 Checkout URL 完成支付。
8. **Postgres 落账(第二段:提交)**:worker 收到 `checkout.session.completed` webhook(以 Stripe event id 在去重表去重),在单事务内执行:`UPDATE tickets SET quantity_sold = quantity_sold + qty WHERE id = $1 AND quantity_sold + qty = quantity_total`(原子条件更新,最终防线)→ `registration` 置 `confirmed` → ledger 写 `commit` 流水 → 生成入场凭证。提交后 `DEL hold:{holdId}` 并取消对应 `release-hold` 任务。
9. **通知**:确认邮件入队、状态追踪页与 SSE 推送更新(见第 5 章)。
10. **超时释放**:`release-hold` 触发时若 registration 仍为 `awaiting_payment`:置 `expired`,ledger 写 `release`,`INCRBY stock:{ticketId}` 归还库存,`DEL hold`;随后检查候补名单并触发晋升(见第 4 章)。若已 `confirmed` 则任务空转退出。
11. **对账**:worker 每 60 秒比对 Postgres 口径余量与 Redis `stock` 值,偏差以 Postgres 为准回写 Redis 并记录告警——预扣层允许短暂不准,落账层永远精确。

```ts
// apps/api/src/registrations/reserve.lua(经 ioredis defineCommand 注册)
const RESERVE_LUA = `
local stock = tonumber(redis.call('GET', KEYS[1]) or '-1')
if stock < 0 then return redis.error_reply('STOCK_NOT_LOADED') end
if stock < tonumber(ARGV[1]) then return 0 end
redis.call('DECRBY', KEYS[1], ARGV[1])
redis.call('SET', KEYS[2], ARGV[1], 'EX', ARGV[2])
return 1
`; // KEYS: stock:{ticketId}, hold:{holdId}  ARGV: qty, ttlSeconds
```

| 故障点 | 后果 | 恢复机制 |
| --- | --- | --- |
| API 在步骤 4 与 5 之间崩溃 | Redis 已扣、无落账、无 BullMQ 任务 | `hold` TTL 过期由 keyspace notification 兜底归还;60 秒对账兜双重底 |
| Stripe webhook 重复投递 | 可能重复提交库存 | event id 去重表,重复投递 no-op |
| 步骤 8 条件更新影响 0 行(容量被下调) | 已付款但无票 | registration 置 `cancelled` 并触发退款流程,通知组织者 |
| Redis 重启丢失 stock 键 | Lua 返回 `STOCK_NOT_LOADED` | worker 从 Postgres 重建;重建期间 API 降级为直接 Postgres 原子扣减(牺牲吞吐不牺牲正确性) |
| 用户重复提交 / 网络重试 | 可能重复扣减 | 同一幂等键在步骤 3 拦截 |

> **设计要点** ledger(`inventory_ledger`)是这套时序可审计的关键:每笔 reserve/commit/release 都是一条不可变流水,任何时刻 `quantity_sold` 都能由流水重放验证。出现「超卖了吗」的争议时,答案在 ledger 里,不在日志里。

## 13.4 插件架构

插件系统提供四类扩展机制:**filter hook**(可修改数据或否决操作)、**action hook**(只做副作用,失败不阻塞主流程)、**provider slot**(注册一种能力的实现,如支付方式)、**UI slot**(在指定界面位置注入入口)。Stripe 支付(见第 10 章)与企业 SSO(见第 6 章)本身就是走这套机制的一等插件——核心团队与三方开发者用同一套 API,是接口不腐化的唯一保证。插件如需暴露 HTTP 端点(如支付回调、OAuth 回调),统一挂载在 `apps/api` 的 Fastify plugin/hook 体系上——插件 HTTP 挂载点正是 Fastify 在整体架构中的三项职责之一(见第 2 章)。

| hook 名 | 类型 | 触发时机 | 入参 | 能做什么 |
| --- | --- | --- | --- | --- |
| `registration.beforeCreate` | filter | 报名落账事务开始前 | `{ draft, form, event, actor }` | 补全/修改字段;抛 `PluginRejectError` 否决并携带用户可读原因 |
| `registration.afterConfirm` | action | 注册进入 confirmed 后(worker 内) | `{ registration, event }` | 同步 CRM、发放外部凭证等副作用 |
| `registration.stateChanged` | action | 注册状态机任意迁移后 | `{ from, to, registration }` | 外部状态同步、自定义统计 |
| `submission.beforeDecision` | filter | 录用决定写入前 | `{ submission, decision, reviews }` | 校验决定合规性、否决 |
| `submission.afterDecision` | action | 决定生效后 | `{ submission, decision }` | 通知外部系统、触发出版流程 |
| `schedule.afterPublish` | action | 日程版本发布后 | `{ eventId, version, diff }` | 把变更推给日历/直播/会场屏系统 |
| `email.beforeSend` | filter | 邮件进入发送队列前 | `{ message, template, recipient }` | 改写内容、追加附件、按策略否决发送 |
| `webhook.beforeDispatch` | filter | 出站 webhook 投递前 | `{ event, payload, endpoint }` | 改写/过滤出站负载 |
| `payment.provider` | provider | 结算时按活动配置解析 | `PaymentProvider` 接口实现 | 注册新支付方式(微信/支付宝社区插件即此) |
| `auth.provider` | provider | 登录页渲染与回调处理 | `AuthProvider` 接口实现 | 注册企业 SSO(OIDC/SAML) |
| `field.type` | provider | 表单引擎注册字段类型时 | `FieldTypeDef`(Zod schema + 渲染器) | 自定义报名/投稿字段类型(见第 4 章) |
| `export.format` | provider | 导出菜单渲染与执行 | `Exporter` 接口实现 | 新增导出格式 |
| `ui.admin.nav` | UI slot | 管理后台导航渲染 | `{ eventId, role }` | 注入插件设置页入口 |
| `ui.public.head` | UI slot | 公共页 head 渲染 | `{ event, page }` | 注入 JSON-LD 补充、统计脚本(受 CSP 白名单约束,见第 12 章) |
| `cron.schedule` | action | 按 cron 表达式由 worker 调度 | `{ now }` | 周期任务(同步、清理、报表) |

插件生命周期:

1. **发现**:npm 包名前缀 `yumeet-plugin-*`,或从插件市场安装(见第 14 章);
2. **安装**:校验签名与 `yumeet.plugin.json` manifest,向管理员展示其声明的权限与网络访问清单,确认后落库;
3. **迁移**:插件自带的 Drizzle 迁移在独立 schema(`plugin_{name}`)内执行,禁止触碰核心表;
4. **启用/配置**:hook 注册生效,配置项由插件的 Zod schema 自动生成后台表单;
5. **禁用**:hook 立即摘除,数据保留;
6. **卸载**:提示是否保留插件 schema 数据,默认保留 30 天后清理。

权限与沙箱按信任级别分两档:核心插件(仓库内维护)进程内运行;三方插件在 `node:worker_threads` 隔离运行,与主进程通过 structured clone RPC 通信,单次 hook 调用超时 5 秒、内存上限 256 MB,出站网络仅限 manifest 中 `network.allowlist` 声明的域名。三方插件**没有数据库句柄**,只能调用按 manifest `permissions`(如 `registrations:read`、`email:send`)裁剪过的 Plugin API——权限模型与第 6 章的能力表同源。

> **Indico 教训** Indico 插件通过 Python entry points 加载后可直接 import 内部模块、任意触库,导致每次升级都可能破坏插件,且插件缺陷等价于核心缺陷(其 SSRF 漏洞即由信任边界模糊放大,见第 12 章)。yuMeet 用声明式权限 + 进程隔离把「插件出错」与「系统出错」切开。

```ts
// yumeet-plugin-slack/src/index.ts
import { definePlugin } from '@yumeet/sdk';

export default definePlugin({
  name: 'slack-notify',
  configSchema: z.object({ webhookUrl: z.string().url() }),
  hooks: {
    'registration.afterConfirm': async ({ registration, event }, ctx) => {
      await ctx.fetch(ctx.config.webhookUrl, {   // ctx.fetch 受 allowlist 约束
        method: 'POST',
        body: JSON.stringify({ text: `${event.title} 新增报名` }),
      });
    },
  },
});
```

## 13.5 自动化规则引擎

规则引擎让组织者不写代码就能表达「当 X 发生、若满足 Y、则执行 Z」,是渐进披露原则在自动化上的体现:简单场景用后台的规则构建器点选,高级场景直接编辑 JSON。规则结构固定为 when/if/then 三段:

```json
{
  "name": "学生票欢迎邮件",
  "when": "registration.confirmed",
  "if": { "==": [ { "var": "ticket.code" }, "student" ] },
  "then": [
    { "action": "email.send", "template": "student-welcome" },
    { "action": "tag.add", "tag": "student" }
  ]
}
```

| 段 | 取值 |
| --- | --- |
| when(触发器) | `registration.created/confirmed/cancelled`、`payment.succeeded/failed`、`submission.created/decision`、`checkin.scanned`、`schedule.published`、`waitlist.promoted`、`timer.relative`(相对时刻,如开幕前 24 h) |
| if(条件) | JsonLogic 子集:`==`、`!=`、`>`、``、`in`、`and`、`or`、`var`(取触发事件负载字段,含自定义字段) |
| then(动作) | `email.send`、`tag.add/remove`、`registration.approve`、`waitlist.promote`、`field.set`、`webhook.call`,以及插件经 `rule.action` provider 注册的动作 |

执行语义必须钉死,否则规则引擎会成为事故来源:规则由 worker 在 BullMQ `rules` 队列内执行,at-least-once 投递,因此每个动作以 `hash(ruleId, entityId, triggerEventId)` 为幂等键去重;规则动作产生的事件携带 depth 计数,超过 3 层不再触发任何规则,杜绝循环;失败重试 3 次(指数退避)后进死信并通知组织者。每条规则提供**试运行**(对最近 100 条历史事件回放,只展示「本会执行什么」不真正执行)与逐次执行日志,日志同时写入第 12 章的审计流。

## 13.6 搜索

默认搜索走 Postgres FTS,零额外组件——这是「运维趋零」的直接推论;需要更好的中文分词、拼写容错与毫秒级 facet 时,一个环境变量切到 Meilisearch。两套实现藏在同一个 `SearchDriver` 接口后,上层查询代码不感知差异。

```sql
-- 默认驱动:generated column + GIN,迁移由 Drizzle 管理
ALTER TABLE events ADD COLUMN search tsvector GENERATED ALWAYS AS (
  setweight(to_tsvector('simple', coalesce(title, '')), 'A') ||
  setweight(to_tsvector('simple', coalesce(summary, '')), 'B') ||
  setweight(to_tsvector('simple', coalesce(description_text, '')), 'C')
) STORED;
CREATE INDEX event_search_idx ON events USING gin(search);
CREATE INDEX event_title_trgm_idx ON events USING gin(title gin_trgm_ops);
```

查询侧用 `websearch_to_tsquery('simple', $q)` 支持引号短语与减号排除;对 CJK 输入(无空格分词,`tsquery` 命中率差)自动降级为 `pg_trgm` 相似度检索并按 `similarity` 排序。刻意不采用 zhparser 等分词扩展:它要求编译第三方 C 扩展,破坏「官方 Postgres 镜像直接可用」的部署承诺。中文为主的站点推荐启用 Meilisearch(内建 CJK 分词、typo tolerance、facet):设 `SEARCH_DRIVER=meilisearch` 后,worker 通过事务性 outbox(与第 10 章 webhook 复用同一张表)把 event/submission/speaker 三类文档增量同步到索引,主库始终是事实来源,索引可随时全量重建(`yumeet search reindex`,见第 11 章 CLI)。所有搜索入口在查询层强制权限过滤:匿名请求只命中已发布且未设访问限制的内容,组织者搜索附带其角色可见范围——过滤在驱动层做,杜绝「先查后滤」的越权泄漏(见第 12 章)。
