# 第 7 章 · 模板与主题系统

yuMeet 的硬约束之一是「简单用」与「高端自定义」并存:小研讨会组织者上传一个 logo 就该得到体面的活动站,大型机构则要能把整套前端换成自己的。本章定义支撑这条约束的四层自定义模型、design token 体系、模板包(theme package)格式,并给出默认主题 Cupertino 的完整视觉规范——所有主题的字阶、色板、间距数值以本章为唯一基准,第 8 章的组件与交互规范建立在这些 token 之上。

## 7.1 四层自定义模型

自定义能力按投入成本分为 L0 到 L3 四层。设计原则:**每一层都是完整可用的终点,而不是通往下一层的半成品**;从 L0 走到 L3 的过程中,前一层的配置不作废(L3 除外,它绕过渲染层)。绝大多数用户应当停在 L0——这是「复杂度按需渐进披露」在主题系统上的直接体现。

| 层 | 名称 | 操作方式 | 能改什么 | 不能改什么 | 停在这一层的用户 |
| --- | --- | --- | --- | --- | --- |
| L0 | 开关配置 | 管理后台表单,零代码 | logo、主色(单个色值,系统自动派生 hover/深色变体)、hero 图或视频、页脚文案、模块开关(是否显示讲者墙/赞助商/日程) | 布局结构、字体、组件样式 | 约 90% 的组织者:高校课题组、系列研讨会、部门内训。判断标准:没有专职设计师 |
| L1 | Design tokens | 后台 token 编辑器,或上传 `kind: "tokens"` 主题包(仅 CSS 与静态资源,不含代码) | 7.2 节定义的全部语义 token:完整色板、字体栈与自托管字体、圆角、间距密度、阴影 | 页面结构、组件 DOM、交互逻辑 | 有品牌 VI 手册的机构:学会年会、企业大会。判断标准:有设计师、无前端工程师 |
| L2 | 模板包 | 编写含 React 组件的主题包(`kind: "code"`),经 yumeet CLI 安装 | 页面 slot 级布局覆盖、组件覆盖、新增页面区块、主题自带配置项 | 数据模型、API、工作流 | 有前端工程师的机构、主题作者与社区。判断标准:能维护一个 npm 包 |
| L3 | Headless API | 完全自建前端,经 REST API(OpenAPI 3.1,见第 10 章)读写数据 | 一切呈现层。活动数据嵌入自有 CMS、官网或小程序 | ——(报名、支付等写路径仍走 yuMeet API 与托管表单) | 大型机构官网团队。判断标准:已有自己的前端基础设施与发布流程 |

层与层的衔接规则:L1 的 token 覆盖叠加在 L0 之上;L2 主题包声明 `extends` 继承链,未覆盖的 slot 与 token 自动回落(见 7.3);L0/L1 的后台配置作为 `settings` 注入 L2 组件,因此换用 L2 主题后,组织者此前在后台填的 logo 与主色依然生效。L3 是唯一「跳出」渲染层的选择,官方提供 `@yumeet/sdk`(TypeScript 客户端,由 OpenAPI 生成)降低起步成本。

> **Indico 的教训**:Indico 的定制手段是编写 Python 插件覆盖 Jinja 模板,改动需要重新部署并随版本升级反复适配;没有中间层,导致大量机构直接在生产实例上注入 CSS hack,升级即碎。yuMeet 用 L0/L1 吸收 80% 的定制需求(纯数据,升级零成本),把「写代码」推迟到确有前端团队的 L2,并以 manifest 版本约束(`engines.yumeet`)显式管理兼容性。

## 7.2 Design Token 体系

Token 是主题系统的通用语言:L0 的主色选择器、L1 的 token 编辑器、L2 模板包的 `tokens.css`、第 8 章设计系统的组件,读写的是同一组 CSS custom properties。Tailwind CSS v4 通过 `@theme` 把这组变量映射为 utility class,组件代码不直接出现色值。

**命名规范**:`--yu-{类别}-{角色}-{变体}`,全小写、连字符分隔。类别取值:`color`、`font`、`text`(字阶)、`space`、`radius`、`shadow`、`motion`、`z`。禁止在语义层出现具体颜色名(不允许 `--yu-color-blue` 作为语义 token)。

**三层结构**:

1. **原始层(primitive)**:裸值,如 `--yu-blue-500: #0071e3`。仅供语义层引用,组件与模板禁止直接使用。
2. **语义层(semantic)**:按用途命名,如 `--yu-color-accent`、`--yu-color-bg-section`。*主题定制的目标层*——L1 编辑器只暴露这一层,约 60 个 token。深浅色切换发生在这一层:同名 token 在 `[data-theme="dark"]` 作用域下重新赋值,组件无感知。
3. **组件层(component)**:仅当组件需要偏离语义默认值时才定义,如 `--yu-button-primary-bg`,默认引用语义层。数量控制在必要最小,避免 token 爆炸。

```css
/* packages/ui/tokens.css —— 节选 */
:root {
  /* L1 原始层 */
  --yu-blue-500: #0071e3;
  --yu-blue-450: #0077ed;
  --yu-blue-300: #2997ff;

  /* L2 语义层(浅色为默认) */
  --yu-color-bg-page: #ffffff;
  --yu-color-bg-section: #f5f5f7;
  --yu-color-text-primary: #1d1d1f;
  --yu-color-text-secondary: #6e6e73;
  --yu-color-hairline: #d2d2d7;
  --yu-color-accent: var(--yu-blue-500);
  --yu-color-accent-hover: var(--yu-blue-450);

  --yu-font-family-base: system-ui, -apple-system, "SF Pro Text", "Segoe UI",
    "Helvetica Neue", "PingFang SC", "Microsoft YaHei", sans-serif;
  --yu-radius-control: 10px;   /* 允许区间 8-12px */
  --yu-radius-card: 18px;
  --yu-space-1: 4px;           /* 8pt 网格,见 7.4 */

  /* L3 组件层(按需) */
  --yu-button-primary-bg: var(--yu-color-accent);
  --yu-nav-height: 48px;
  --yu-nav-bg: rgba(251, 251, 253, 0.8);
}

[data-theme="dark"] {
  --yu-color-bg-page: #000000;
  --yu-color-bg-section: #161617;
  --yu-color-text-primary: #f5f5f7;
  --yu-color-text-secondary: #86868b;
  --yu-color-hairline: rgba(255, 255, 255, 0.16);
  --yu-color-accent: var(--yu-blue-300);
  --yu-color-accent-hover: #4dabff;
  --yu-nav-bg: rgba(22, 22, 23, 0.8);
}
```

深浅色策略:公共活动站默认跟随 `prefers-color-scheme`,并在导航提供三态切换(浅/深/跟随系统),选择持久化到 cookie 以便 RSC 首屏直出正确的 `data-theme`,避免闪烁。主题包可声明 `darkMode: "none"` 表示只提供单一外观(如品牌强制浅色),此时切换器隐藏。

> **设计要点**:L0 的「主色」单值配置在服务端派生完整色阶——用 OKLCH 色彩空间生成 hover(亮度 +4%)、深色模式变体(提高明度与色度以保证黑底可读)、以及与前景色的对比度校验;对比度不足 4.5:1 时后台直接给出警告与建议值,而不是让组织者上线后才发现按钮文字看不清。这是「默认即合规」原则在主题层的落点。

## 7.3 模板包格式

模板包是一个以 `theme.json` 为 manifest 的目录,可发布为 npm 包或打包为 zip。两种类型:`kind: "tokens"` 只含 `tokens.css`、字体与图片,*不含可执行代码*,可由组织管理员在后台直接上传,SaaS 与自托管均安全;`kind: "code"` 含 React 组件,因为会在服务端执行,只能由平台管理员经 `yumeet theme add` 安装(自托管),或经官方市场审核后上架(SaaS)。

```json
{
  "$schema": "https://yumeet.dev/schemas/theme.v1.json",
  "name": "@acme/yumeet-theme-aurora",
  "displayName": "Aurora",
  "version": "1.2.0",
  "license": "MIT",
  "kind": "code",
  "engines": { "yumeet": ">=1.0.0 <2.0.0" },
  "extends": "@yumeet/theme-cupertino",
  "darkMode": "auto",
  "tokens": "./tokens.css",
  "assets": "./assets",
  "preview": "./assets/preview.png",
  "fonts": [
    {
      "family": "Inter Variable",
      "src": "./assets/fonts/inter-var.woff2",
      "weight": "100 900",
      "display": "swap"
    }
  ],
  "slots": {
    "event.hero": "./slots/EventHero.tsx",
    "event.footer": "./slots/EventFooter.tsx",
    "schedule.session-card": "./slots/SessionCard.tsx"
  },
  "components": {
    "Button": "./components/Button.tsx"
  },
  "settings": [
    {
      "key": "heroStyle",
      "type": "select",
      "label": "Hero 布局",
      "options": ["centered", "split", "video"],
      "default": "centered"
    },
    {
      "key": "showSponsorBar",
      "type": "boolean",
      "label": "显示赞助商栏",
      "default": true
    }
  ]
}
```

**Slot 机制**:每个公共页面被切分为一组命名 slot,主题按 slot 粒度覆盖,而不是整页替换——这样 yuMeet 升级页面骨架(SEO、无障碍、结构化数据)时,主题作者的覆盖不受影响。核心 slot 一览:

| Slot 名 | 所在页面 | 默认内容 |
| --- | --- | --- |
| `site.header` / `site.footer` | 全站 | 毛玻璃导航 / 页脚 |
| `event.hero` | 活动首页 | 标题、日期地点、报名 CTA |
| `event.about` / `event.speakers` / `event.venue` | 活动首页 | 介绍分区 / 讲者墙 / 场地与地图 |
| `schedule.timeline` / `schedule.session-card` | 日程页 | 多轨时间轴 / 单场卡片 |
| `registration.intro` / `registration.confirmation` | 报名流程 | 表单前说明 / 成功页 |

解析顺序(编号即优先级):1. 当前主题的 `slots` 映射;2. `extends` 链逐级向上查找;3. Cupertino 内置默认实现。`components` 覆盖同理,但作用于 Cupertino UI 的具名组件(如 `Button`、`EventCard`),影响所有引用处。Slot 组件是 React Server Component,收到的 props 由 `@yumeet/theme-kit` 提供类型,包含只读活动数据、后台配置(`settings`,含 L0 的 logo 与主色)与 i18n 函数;不允许在 slot 内直接访问数据库或发起任意网络请求(CSP 与运行时白名单约束,见第 12 章)。一个 slot 覆盖示例:

```ts
// slots/EventHero.tsx —— 覆盖活动首页 hero
import type { SlotProps } from '@yumeet/theme-kit';
import { RegisterCta, FormattedDateRange } from '@yumeet/theme-kit/components';

export default function EventHero({ event, settings, t }: SlotProps<'event.hero'>) {
  return (
    <header className={`hero hero--${settings.heroStyle}`}>
      <p className="hero-kicker">{event.series?.name}</p>
      <h1 className="hero-title">{event.title}</h1>
      <p className="hero-meta">
        <FormattedDateRange start={event.startsAt} end={event.endsAt} />
        {' · '}{event.venue?.city ?? t('event.online')}
      </p>
      <RegisterCta event={event} /> {/* 报名状态机由系统组件承载,主题不可绕过 */}
    </header>
  );
}
```

> **设计要点**:`RegisterCta` 这类涉及状态与写路径的组件是「受保护组件」——主题可以改它的位置与外层样式,但不能覆盖其实现。报名按钮的候补/售罄/审批中等状态展示(第 5 章状态机)必须全站一致,这条边界防止主题作者无意间破坏核心流程。

## 7.4 默认主题 Cupertino 完整规范

Cupertino 是内置默认主题,采用 apple.com 视觉语言:大留白、系统字体、克制的单一强调色、毛玻璃导航。以下数值即 `@yumeet/theme-cupertino` 的 token 实现,也是全文档视觉基准。

### 7.4.1 字阶表

字体栈:`system-ui, -apple-system, "SF Pro Text", "Segoe UI", "Helvetica Neue", "PingFang SC", "Microsoft YaHei", sans-serif`。字阶共 11 级,token 形如 `--yu-text-*`;40px 及以上西文标题使用负字距,移动端(&lt;735px)display 与 title 级按表内括号值降档。

| Token | 用途 | px(移动端) | 行高 | 字重 | 字距 |
| --- | --- | --- | --- | --- | --- |
| `display-1` | 活动首页 hero 主标题 | 80(48) | 1.05 | 600 | -0.015em |
| `display-2` | 次级 hero、落地分区大标题 | 56(40) | 1.07 | 600 | -0.012em |
| `title-1` | 页面一级标题(日程页、讲者页) | 48(32) | 1.08 | 600 | -0.008em |
| `title-2` | 分区标题 | 40(28) | 1.10 | 600 | -0.005em |
| `title-3` | 卡片组标题、对话框标题 | 28(24) | 1.14 | 600 | 0 |
| `headline` | 卡片标题、日程场次名 | 21 | 1.30 | 600 | 0.011em |
| `body-large` | hero 副标题、导语 | 21 | 1.45 | 400 | 0.011em |
| `body` | 正文 | 17 | 1.60 | 400 | -0.022em |
| `callout` | 表单标签、次要正文 | 15 | 1.45 | 400 | -0.016em |
| `footnote` | 元信息、时间戳、徽标文字 | 14 | 1.42 | 400 | -0.012em |
| `caption` | 图注、法务文字 | 12 | 1.35 | 400 | 0 |

中文排版修正:字阶最重字重取 600 而非 700,恰在 `"PingFang SC"` 真字重范围内,避免伪加粗;中文标题不应用负字距(经 `:lang(zh)` 将 display/title 级字距归零),中西文混排间隙由 `text-autospace` 处理,详见第 8 章 8.8。

### 7.4.2 浅深色色板对照表

| 语义 Token(前缀 `--yu-color-`) | 用途 | 浅色 | 深色 |
| --- | --- | --- | --- |
| `bg-page` | 页面底色 | #ffffff | #000000 |
| `bg-section` | 分区底色(与页面底交替) | #f5f5f7 | #161617 |
| `bg-elevated` | 卡片、对话框、弹层 | #ffffff | #1d1d1f |
| `text-primary` | 正文 | #1d1d1f | #f5f5f7 |
| `text-secondary` | 次要文字、元信息 | #6e6e73 | #86868b |
| `hairline` | 发丝线、分隔线、描边 | #d2d2d7 | rgba(255,255,255,0.16) |
| `accent` | 链接、主按钮、选中态 | #0071e3 | #2997ff |
| `accent-hover` | 上述 hover | #0077ed | #4dabff |
| `success` / `success-text` | 报名成功、录用(填充 / 文字两档) | #34c759 / #248a3d | #30d158 / #30d158 |
| `warning` / `warning-text` | 候补、临近截止(填充 / 文字两档) | #ff9500 / #c93400 | #ff9f0a / #ff9f0a |
| `danger` / `danger-text` | 失败、拒绝、破坏性操作(填充 / 文字两档) | #ff3b30 / #d70015 | #ff453a / #ff453a |
| `focus-ring` | 键盘聚焦环(不透明实色,对相邻底色 ≥3:1,WCAG 1.4.11) | #0071e3 | #2997ff |
| `focus-ring-soft` | 输入框聚焦内圈(唯一保留的半透明聚焦值,仅此用途) | rgba(0,113,227,0.18) | rgba(41,151,255,0.22) |

状态色分「填充 / 文字」两档:填充档(#34c759 / #ff9500 / #ff3b30)用于徽标底、图形与状态点;文字档刻意取深(如 success 文字用 #248a3d 而非 #34c759),保证在白底上作为文字使用时达到 WCAG AA 的 4.5:1。深色模式下亮色在黑底上本身达标,两档合一。使用规则见第 8 章 8.2。

### 7.4.3 间距、导航、hero 与卡片

**间距**:8pt 网格,token `--yu-space-{n}`,n 为 4px 的倍数:1=4、2=8、3=12、4=16、6=24、8=32、12=48、16=64、24=96、30=120。组件内部用 2/3/4,组件之间用 6/8,分区纵向留白桌面端 24(96px)、移动端 16(64px),hero 上下用 30(120px)。禁止出现网格外数值。

**导航**:高度桌面 48px、移动 44px;底色 `rgba(251,251,253,0.8)`(深色 `rgba(22,22,23,0.8)`)加 `backdrop-filter: blur(20px) saturate(180%)`;底边 1px 发丝线仅在页面滚动超过 8px 后淡入;内容为左侧活动名(footnote 级、字重 600)、中部锚点导航、右侧报名 CTA;粘性定位,滚动时不收缩不变高。

**Hero**:居中单列,宽度上限 980px;结构自上而下为系列名 kicker(footnote、secondary 色)、`display-1` 标题、`body-large` 副标题(日期、地点,secondary 色)、CTA 行(主按钮「立即报名」+ 文字链「查看日程 ›」,链接 accent 色带右侧 chevron);背景默认纯页面底色,组织者上传的 hero 媒体以 16:9 圆角 18px 呈现在 CTA 下方而非铺满背景,保证标题对比度恒定。

**卡片**:圆角 18px,底色 `bg-elevated`,置于 `bg-section` 分区上时依靠底色差与发丝线区分,不加阴影;悬浮弹层(菜单、popover)使用两级阴影之一(第 8 章 8.3)。可点击卡片 hover 时上移 2px 并加 `0 8px 24px rgba(0,0,0,0.08)` 阴影,spring 参数与降级策略见第 8 章 8.4。内边距桌面 32px、移动 24px;卡片标题用 `headline`,元信息用 `footnote`。

## 7.5 主题切换与实时预览

入口在管理后台 `/manage//design`,同一编辑器承载 L0 与 L1(高级模式折叠展开,再次体现渐进披露)。体验设计成「所见即所得、发布前不影响线上」:

1. 左栏为分组 token 编辑器(品牌 / 色彩 / 字体 / 形状)与主题选择器;右栏是一个 iframe,渲染*真实活动页*(取该组织最近的活动,无活动则用内置示例数据),而非静态缩略图。
2. 每次修改写入该组织的 **draft token set**(数据库 JSONB,含乐观锁版本号),同时经 `postMessage` 推给 iframe,预览脚本直接改写 CSS custom properties——不触发重新构建,变更在 100ms 内可见。
3. 预览工具栏提供:浅/深色切换、375/768/1280px 断点切换、页面切换(首页/日程/报名表单),保证组织者在发布前看过全部关键页面的两种外观。
4. 「发布」将 draft 固化为不可变的 theme version(顺序编号,记录操作者与 diff),写入 `theme_version` 表,随后调用 `revalidateTag('theme:')` 失效 ISR 缓存;公共页在下一次请求重新生成,发布到全站生效典型延迟低于 10 秒。
5. 历史版本列表支持一键回滚——回滚即把旧版本重新发布为新版本,不做原地覆盖,审计链完整(见第 12 章)。
6. 安装 L2 主题包后,其 `settings` 声明自动渲染为编辑器中的「主题选项」分组;切换主题时,L0/L1 配置保留并继续注入新主题。

> **设计要点**:预览 iframe 加载的是带 `?preview=` 的真实渲染路径,服务端校验当前会话对该组织的 `design.edit` 能力后才应用 draft token,该 URL 对外无效——预览通道不成为未发布内容的泄露面。

## 7.6 自定义域名与白标

组织可绑定自有域名(如 `events.acme.org`),粒度为组织级,活动落在该域名的路径下(URL 规则见第 3 章 3.4)。绑定流程:

1. 组织管理员在 `/manage//settings/domain` 填入域名,系统生成两条待配置 DNS 记录:CNAME 指向实例入口(SaaS 为 `edge.yumeet.app`,自托管为主域名),以及一条 `_yumeet-challenge` TXT 验证记录。
2. worker 每 60 秒轮询 DNS,两条记录均命中后将域名写入 `custom_domain` 表并标记 `verified`;页面上的状态展示复用第 5 章的「物流式」进度组件(待配置 → 检测中 → 已验证 → 证书就绪)。
3. 证书由 Caddy on-demand TLS 自动签发:Caddy 的 `ask` 端点指向 `api` 的内部路由 `/internal/tls-allowed?domain=`,仅对 `verified` 域名返回 200,防止任意域名骗取证书与资源耗尽。
4. web 应用按 `Host` 头解析租户:中间件查 `custom_domain` → 组织映射(Redis 缓存,TTL 5 分钟,发布时主动失效),原平台域名下的旧 URL 301 到新域名,canonical 与 sitemap 同步切换,SEO 权重不流失。

**白标**是在自定义域名之上移除 yuMeet 自身痕迹,按接触面逐项配置:

| 接触面 | 配置项 | 默认 | 说明 |
| --- | --- | --- | --- |
| 页脚署名 | `branding.hidePoweredBy` | 显示「Powered by yuMeet」 | 自托管可直接关闭;SaaS 属付费能力(见第 14 章商业策略) |
| 邮件发信域 | `email.fromDomain` | 平台域 | 引导配置 SPF/DKIM/DMARC 三条记录,验证通过前不允许切换——防止组织者把自己的确认邮件送进垃圾箱(Indico 教训,见第 1 章 1.1) |
| 邮件模板 | react-email 布局 token | Cupertino 邮件版式 | logo、主色随 L0/L1 配置;结构不可改,保证送达与渲染兼容性 |
| PDF/胸牌 | 证书与胸牌模板变量 | 含组织 logo | satori 模板读取同一组品牌 token(见第 5 章) |
| ICS 订阅 | `PRODID` 与日历名 | `-//yuMeet//` | 白标后使用组织名 |
| 浏览器侧 | favicon、PWA manifest 名称与图标 | yuMeet 图标 | 随 L0 的 logo 配置自动生成各尺寸 |

边界声明:白标不改变管理后台(`/manage` 始终为 yuMeet 品牌),也不豁免第 12 章的隐私页与法务页——组织可换皮,合规内容必须在场。
