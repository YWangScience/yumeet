# 第 12 章 · 安全、隐私与合规

本章从威胁模型出发,逐条对照 Indico 历史上三类真实漏洞(BOLA、SSRF、批量导出)给出 yuMeet 的结构性防御,然后定义安全基线、隐私默认值、GDPR 合规的产品化实现与不可篡改审计日志。原则只有一条:安全属性必须由架构保证,而非依赖开发者「每次都记得检查」。

## 12.1 威胁模型:以 Indico 的三类漏洞为镜

yuMeet 保护的核心资产与对应的主要对手如下:

| 资产 | 主要威胁 | 防御落点 |
| --- | --- | --- |
| 参会者 PII(姓名、邮箱、饮食/无障碍需求) | 横向越权读取、批量爬取、内部滥用 | 12.1 防御一/三、12.3、12.5 |
| 投稿与评审内容 | 双盲破坏、竞争对手窃取 | 第 6 章序列化脱敏、12.2 |
| 支付凭据与订单 | 凭证窃取、退款欺诈 | Stripe 托管卡数据、step-up、12.5 |
| 会话与 API 凭证 | CSRF、令牌重放、钓鱼 | 第 6 章 6.3 节 |
| 服务器与内网 | SSRF、供应链投毒、上传恶意文件 | 12.1 防御二、12.2 |

Indico 二十年的漏洞史里有三类教训最具代表性,yuMeet 把每一类都转化为一条**架构级**防御——不是修一个 bug,而是让同类 bug 无处生长。

### 教训一:BOLA——/api/principals 的对象级授权缺失

> **Indico 教训**:Indico 的 `/api/principals` 端点允许任何已登录用户以数字 ID 批量查询任意用户的姓名、邮箱与所属机构——典型的 Broken Object Level Authorization(OWASP API Top 10 第 1 位):端点校验了「你登录了吗」,却没校验「这个对象跟你有什么关系」。顺序数字 ID 让全量枚举只需一个 for 循环。

yuMeet 的对应防御,按纵深排列:

1. **不存在全局用户查询端点**。用户搜索仅存在于「团队邀请」上下文,要求 `team.manage` 能力,且只返回同组织成员的显示名——最危险的端点,直接不造。
2. **先加载、后鉴权的强制中间件**:每个资源型入口(Server Action 或 REST 路由)必须声明能力并通过资源加载器取得对象,鉴权函数 `can(actor, capability, resource)` 在拿到具体对象后才放行(代码见 12.2)。「忘记检查」在这套模式里表现为编译失败,而不是线上漏洞。
3. **主键全部为 UUIDv7**,对外 API 与永久链接只暴露带类型前缀的编码 ID(`evt_` / `reg_` 等,见第 9 章 9.1),不可枚举;跨租户访问返回 404 而非 403,不充当「资源存在性预言机」。
4. **响应白名单序列化**:所有对外 DTO 经 Zod output schema 过滤,字段是显式列出的,不存在 ORM 对象「顺手带出」邮箱哈希或内部备注的路径。
5. **CI 静态检查**:自研 ESLint 规则扫描 `apps/api` 与 `apps/web`,任何未声明能力、或绕过 `eventProcedure`/`orgProcedure` 工厂的资源入口无法合并。

### 教训二:SSRF——让服务器替攻击者访问内网

> **Indico 教训**:Indico 曾存在 SSRF 缺陷——服务器按用户提供的 URL 发起抓取,攻击者借此触达内网服务与云元数据端点(如 `169.254.169.254`),把一个「取远程资源」的便利功能变成内网探针。

yuMeet 中所有出站 HTTP(webhook 投递、外部日历抓取、OIDC discovery、直播封面图代理)必须经过唯一的 `safeFetch` broker,业务代码无权直接发起网络请求:

```ts
// packages/net/src/safe-fetch.ts(节选)
export async function safeFetch(rawUrl: string, opts: SafeFetchOpts) {
  const url = new URL(rawUrl);
  if (url.protocol !== 'https:') throw new SsrfError('scheme');   // 仅 https
  const addrs = await resolveAll(url.hostname);                   // 先解析全部 A/AAAA
  if (addrs.some(isPrivateOrReserved))                            // RFC1918、127/8、
    throw new SsrfError('private-ip');                            // 169.254/16、fc00::/7 等
  return request(url, {
    connect: { lookup: pinTo(addrs) },   // 连接钉住已校验 IP,封死 DNS rebinding
    maxRedirections: 0,                  // 重定向逐跳重新走完整校验
    headersTimeout: 5_000,
    bodyTimeout: 10_000,
    maxResponseSize: 5 * 1024 * 1024,
  });
}
```

配套约束:webhook 目标 URL 在**保存时与每次投递时**都重新校验(防 TOCTOU:先指向合法域名、审核通过后再改 DNS 指向内网);出站请求全部由 worker 容器执行,compose 部署文档要求在防火墙层额外封禁 worker 到内网段与元数据地址的 egress,作为代码之外的第二道闸;ESLint 禁止在业务模块直接 import `undici`/`fetch`。Webhook 的 HMAC 签名与重试语义见第 10 章。

### 教训三:批量导出——把「一条」的授权当成「全部」的授权

> **Indico 教训**:Indico 曾出现用户资料可被批量导出/爬取的问题——单条读取有权限,但系统没有把「规模」本身当作需要授权的维度,聚合之后的参会者名单成了现成的营销与钓鱼数据集。

yuMeet 把「批量」定义为一种独立的、更昂贵的操作:

1. **导出是独立能力** `registration.export`,预设仅组织者持有(见第 6 章能力矩阵),协作者日常工作不需要、也拿不到全量数据。
2. **导出必须 step-up**:10 分钟内的 passkey/magic link 重验证,防会话劫持者顺手拖库。
3. **导出走异步任务**:BullMQ 生成文件、24 小时链接、邮件通知;每次导出写审计事件(who/what/row_count/ip),产物内嵌导出者与时间戳水印列——泄露可溯源。
4. **列表 API 强制游标分页**:默认 20 行、上限 100 行(见第 10 章 10.2),无 `?limit=999999` 逃生门;配合 12.2 的速率限制,低速爬取在配额上不可行。
5. **公开面最小化**:参会者名单默认不公开,公开需参会者本人 opt-in(见 12.3),即使组织者配置失误,未同意者也不会出现在任何公共响应里。

> **设计要点**:三条防御的共性是把安全判断从「散落在各处的 if」收敛为三个单点:授权中间件、出站 broker、导出管线。单点可以被穷尽测试,散落的 if 不能。

## 12.2 安全基线

**对象级授权中间件**是全部 API 的骨架,资源路由只能经由能力工厂构造:

```ts
// packages/core/src/authz/authorize.ts(节选)
// 能力工厂:apps/web 的 Server Actions 与 apps/api 的 REST 路由共用同一入口
export const eventProcedure = (capability: Capability) =>
  defineProcedure({
    input: z.object({ eventId: z.string().uuid() }).passthrough(),
    async authorize(ctx, input) {
      const event = await ctx.loaders.event.load(input.eventId); // 1. 先加载对象
      if (!event) throw NOT_FOUND;
      if (!(await can(ctx.actor, capability, event)))            // 2. 能力 + 租户
        throw NOT_FOUND;                                         // 3. 统一 404,不当预言机
      return { ...ctx, event };                                  // 4. 已授权对象注入下游
    },
  });

// 用例:未写 capability 参数直接编译不过
export const exportRegistrations =
  eventProcedure('registration.export').handler(/* ... */);
```

基线其余各项:

- **输入校验**:Server Actions 与 REST 的每个入口都有 Zod schema,REST 侧由同一 schema 生成 OpenAPI 3.1(见第 10 章);自定义表单字段的 JSONB 载荷按表单定义动态生成 Zod 校验器(见第 9 章),未知键一律剥离。
- **CSP**:严格默认,活动若配置直播嵌入,仅把该活动声明的 provider 域追加进 `frame-src`:

- ```http
Content-Security-Policy:
  default-src 'self';
  script-src 'self' 'nonce-{per-request}';
  style-src 'self' 'unsafe-inline';
  img-src 'self' data: blob: https://{minio-host};
  connect-src 'self' https://{minio-host};
  frame-src https://www.youtube-nocookie.com https://player.vimeo.com;
  object-src 'none'; base-uri 'none'; form-action 'self';
  frame-ancestors 'none'
```
- **速率限制**(Redis 滑动窗口,按端点分类):

| 端点类别 | 限额 | 超限行为 |
| --- | --- | --- |
| magic link 申请 | 5 次/邮箱/小时,20 次/IP/小时 | 静默成功(不泄露邮箱是否存在),不发信 |
| 登录/令牌校验 | 10 次/IP/分钟 | 429 + 指数退避提示 |
| 公共读(活动页 API、ICS) | 120 次/IP/分钟 | 429,CDN 缓存兜底 |
| 认证写操作 | 60 次/用户/分钟 | 429 |
| 报名提交 | 10 次/IP/分钟;抢票场景切换为排队模式(见第 13 章) | 进入队列而非报错 |
| 数据导出 | 5 次/用户/天 | 拒绝并提示联系组织 Owner |

- **上传管线**:① 预签名直传 MinIO 隔离桶;② worker 以 magic bytes 嗅探真实 MIME 并与声明比对;③ 图片一律重编码(顺带剥 EXIF),SVG 光栅化或经白名单 sanitizer;④ 可选 ClamAV 容器扫描(compose profile 一键启用);⑤ 移入服务桶,从独立源站域名以 `Content-Disposition: attachment` + `X-Content-Type-Options: nosniff` 供给,杜绝同源脚本执行。
- **依赖与供应链**:pnpm lockfile 在 CI 冻结安装;Renovate 每周升级 + 自动化测试门禁;`pnpm audit` 高危即阻断;Docker 镜像非 root、最小基底、按 digest 固定并 cosign 签名;每个 release 附 SBOM(syft 生成)。

## 12.3 隐私默认:合规不是开关,是出厂设置

「默认即合规」原则(第 1 章)在数据层的落点是三件事:少收集、少展示、按时删。

1. **数据最小化在表单设计器里执行**:新建报名表默认只有邮箱与姓名;组织者添加出生日期、证件号、饮食/无障碍需求等字段时,设计器内联提示该字段的风险等级与建议保留期,其中特殊类别数据(健康相关的饮食与无障碍需求)自动标记为「会后 30 天清除」,且默认排除在一切导出模板之外,需逐次显式勾选。
2. **展示默认关闭**:参会者名单、投稿作者页对公众默认不可见;开启后每位参会者在报名流程中单独 opt-in「在公开名单中显示我」,未勾选者从公共 API 与页面双双缺席。邮件营销同意与活动通知分离,前者默认未勾选。
3. **保留期自动清理**:worker 每日运行保留期任务,默认参数如下(组织可调,只能调短或按法务要求调长并留痕):

| 数据 | 默认保留期 | 到期动作 |
| --- | --- | --- |
| 报名 PII(姓名邮箱之外的表单答案) | 活动结束后 730 天(`organizations.retentionDays`,默认 730) | 字段级清除,保留匿名统计 |
| 特殊类别字段(饮食、无障碍) | 活动结束后 30 天 | 硬删除 |
| 邮件送达元数据 | 90 天 | 硬删除 |
| 访问日志(IP、UA) | 90 天 | 硬删除 |
| 未完成的报名草稿 | 30 天 | 硬删除 |
| 审计日志 | 2 年(可配) | 主体假名化后归档 |

匿名化任务与账户注销共用同一套字段级清除引擎(见第 6 章 6.6),保证「到期清理」与「按请求删除」行为一致。归档活动(第 5 章)只保留学术内容与公开元数据,不含报名 PII,因此永久链接与保留期不冲突。

## 12.4 合规:GDPR 权利的产品化实现

每一项数据主体权利都对应一个用户可自助触达的产品功能,而非「发邮件给 DPO 等 30 天」:

| GDPR 权利 | 产品实现 | 入口 |
| --- | --- | --- |
| 知情(Art. 13/14) | 报名页字段旁内联「为什么收集、保留多久」,由字段定义自动生成 | 报名表单 |
| 访问(Art. 15) | 自助导出全部个人数据(JSON + CSV) | 账户页 / 访客状态页 |
| 更正(Art. 16) | 参会者随时经 magic link 管理页修改报名信息(见第 6 章) | 状态追踪页 |
| 删除(Art. 17) | 账户注销流程;访客可单独删除某条报名 | 账户页 / 状态页 |
| 限制处理(Art. 18) | `restricted` 标记:记录冻结,排除于导出、邮件与统计 | 组织者应请求设置,操作入审计 |
| 可携(Art. 20) | 机器可读 JSON,结构随 OpenAPI schema 发布 | 同 Art. 15 导出 |
| 反对(Art. 21) | 一键退订营销邮件;公开名单随时撤回 opt-in | 每封邮件页脚 / 状态页 |
| 免受自动化决策(Art. 22) | 报名审批不提供「自动拒绝」规则,自动化引擎(第 13 章)只能自动通过或转人工 | 产品约束 |

责任划分:自托管场景下部署方是控制者兼处理者,yuMeet 提供隐私政策模板与处理活动记录(RoPA)导出;SaaS 场景 yuMeet 为处理者,提供标准 DPA 与公开的子处理者清单页,子处理者变更提前 30 天邮件通知。**数据驻留**:SaaS 建立区域化部署(EU / US),组织创建时选定区域,数据库、对象存储、备份与日志全部同区,导出任务不跨区执行;自托管天然满足驻留要求。Cookie 层面 yuMeet 只使用严格必要的第一方会话 cookie、无任何第三方跟踪,公共活动站因此无需 cookie banner——这本身就是「组织者复杂度不泄漏到参会者屏幕」的合规版本。

## 12.5 审计日志:可追溯且不可篡改

所有安全相关与数据相关的动作写入 append-only 的 `audit_logs`,采用哈希链使事后篡改可被检测;表结构(字段、哈希链列、INSERT/SELECT-only 权限与按月分区)以第 9 章 9.5 的 `audit_logs` 定义为唯一 schema,此处不再重复。

事件分类与代表事件:

| 分类 | 代表事件 | 必记 meta |
| --- | --- | --- |
| 认证 | `auth.login` / `auth.step_up` / `auth.session_revoke` / `auth.token_reuse_detected` | 方式、设备指纹摘要 |
| 权限 | `role.grant` / `role.revoke` / `role.custom_change` | 目标用户、能力差异 |
| 数据 | `registration.export` / `account.merge` / `account.delete` / `retention.purge` | 行数、字段范围 |
| 财务 | `order.refund` / `payout.config_change` | 金额、订单 id |
| 配置 | `event.publish` / `sso.enforce` / `webhook.create` | 变更前后摘要 |

完整性由三处保障:数据库权限层(应用角色无 UPDATE/DELETE)、哈希链校验(`yumeet doctor --audit-verify` 全链重算,断链即告警,CLI 见第 11 章)、以及每日将当日末条 hash 追加进异地备份清单——篡改历史需同时改库、改链、改备份。组织者在 `/manage` 可按 actor/action/时间过滤查看本组织日志;经 webhook 或 OTLP 可外送 SIEM(见第 10、11 章)。审计日志自身的保留与假名化规则见 12.3。

> **设计要点**:审计事件在授权中间件与导出/财务等单点管线内自动生成,业务代码不手写「记日志」调用——会被忘记的日志等于没有日志。
