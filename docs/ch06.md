# 第 6 章 · 身份、账户与权限

本章定义 yuMeet 的身份分层模型、认证协议栈、会话安全参数、组织与活动两级权限模型(含完整能力矩阵)、多租户隔离机制,以及账户合并、导出与注销的完整流程。所有鉴权决策最终收敛为同一个函数签名 `can(actor, capability, resource)`,该函数也是第 12 章安全基线的地基。

## 6.1 访客优先的身份哲学

Indico 的报名前置条件是创建一个终身账户:填写个人资料、验证邮箱、记住密码,然后才能报名一场可能只参加一次的午间研讨会。yuMeet 反转这个顺序:**报名产生的是一条注册记录,不是一个账户**。账户是参会者在多次交互后自愿「升级」出来的东西,而不是入场券。

身份被划分为四个层级,每层只持有完成当前动作所需的最小凭证:

| 层级 | 名称 | 凭证 | 能做什么 | 数据落点 |
| --- | --- | --- | --- | --- |
| L0 | 匿名访客 | 无(不设跟踪 cookie) | 浏览公共活动站、订阅 ICS、查看已发布日程 | 无 |
| L1 | 访客参会者 | 邮箱验证 + 签名访问链接 | 报名、改签、退款申请、查看状态追踪页、下载票据 | `person` + `registration` 记录,无密码、无账户行 |
| L2 | 正式账户 | passkey / OAuth / magic link 登录 | 跨活动统一管理报名、投稿、个人资料、数据导出 | `user` 记录,与既有 `person` 按已验证邮箱合并 |
| L3 | 组织成员 | L2 + 组织成员关系 | 进入 `/manage`,按角色行使第 6.4 节的能力 | `organization_membership` 记录 |

L1 的访客报名流程如下,全程不出现「设置密码」四个字:

1. 参会者在活动页填写报名表,唯一必填的身份字段是邮箱。
2. 系统写入 `person`(如邮箱已存在则复用)与 `registration`,状态机按票种与审批设置进入初始态(`pending_review` / `awaiting_payment` / `confirmed`,见第 9 章)。
3. 确认邮件包含一条管理链接 `/r/{token}`,token 为一次性换取会话的签名凭证;点开后浏览器获得一个**范围仅限该报名**的受限会话(scope: `registration:{id}`),可查看进度、修改信息、取消报名。
4. 链接失效或换设备时,在状态页输入邮箱即可重发,无「找回密码」概念。
5. 当同一邮箱累计第 2 次报名、或首次投稿时,界面出现一次(且仅一次)非阻断提示:「用 passkey 把这些活动收进一个账户」。拒绝后不再纠缠。

> **设计要点**:受限会话是这套哲学的技术核心——它与正式登录会话走同一套 cookie 机制(6.3 节),差别只在 scope。因此「访客路径」不是旁路,不需要单独的安全审计面。

## 6.2 认证方式与升级路径

yuMeet 不实现密码。四种认证方式全部无密码,按接入成本从低到高排列:

| 方式 | 适用场景 | 实现 | 关键安全参数 |
| --- | --- | --- | --- |
| Magic link | 默认兜底,所有邮箱可用 | 自研,token 只存哈希 | 32 字节随机、TTL 15 分钟、单次使用、同邮箱 5 次失败锁 15 分钟 |
| Passkey | 回访用户主路径,Mac/iPhone 上一次 Touch ID | SimpleWebAuthn,resident key,`userVerification: "preferred"` | challenge 单次使用、绑定 RP ID、注册需已有会话 |
| OAuth | Google / Microsoft / GitHub / Apple | Authorization Code + PKCE | 校验 `state` 与 `nonce`;仅接受 provider 标记已验证的邮箱 |
| 企业 SSO | 机构统一登录 | OIDC 内核,SAML 以插件提供 | 按邮箱域强制路由;JIT provisioning;域所有权经 DNS TXT 验证 |

Magic link 的签发与校验逻辑(节选,完整实现在 `apps/api/src/auth`):

```ts
const token = randomBytes(32).toString('base64url');
await db.insert(loginToken).values({
  tokenHash: sha256(token),            // 库中只存哈希,泄库不可用
  email: normalizedEmail,              // 小写化 + IDN 归一化
  purpose: 'login',                    // 'login' | 'registration_access' | 'step_up'
  expiresAt: addMinutes(now(), 15),
});
// 校验端:常数时间比较哈希;命中立即标记 usedAt(单次使用);
// purpose 不匹配即拒绝 —— 报名管理链接永远换不出登录会话。
```

**升级路径**是身份系统的黏合层:任何 L2 登录成功后,系统按「已验证邮箱」查找散落的 `person` 记录并提示合并(合并流程见 6.6 节)。反向不成立——访客凭证永远无法升级出登录会话,两类 token 的 `purpose` 字段在校验时硬隔离。企业 SSO 域一旦绑定组织并开启强制模式,该域邮箱在所有入口(含 magic link)都会被重定向到 IdP,防止旁路。

## 6.3 会话与凭证安全

会话采用服务端不透明 session + 旋转刷新令牌,不使用可离线验证的 JWT 会话(撤销必须即时生效)。参数如下:

| 项目 | 取值 | 说明 |
| --- | --- | --- |
| 会话 cookie | `__Host-yumeet_s` | httpOnly、Secure、SameSite=Lax、Path=/;值为 128-bit 不透明 id,会话数据存 Redis(热)+ Postgres(源) |
| 访问有效期 | 15 分钟 | 到期由刷新端点静默续期,前端无感 |
| 刷新 cookie | `__Host-yumeet_r` | 按 `__Host-` 规范 Path=/,服务端仅在 `POST /auth/refresh` 处理该 cookie;每次使用即旋转;检测到已旋转令牌被重放时,撤销整个令牌族并通知用户 |
| 滑动过期 | 30 天 | 绝对上限 90 天,到点强制重新认证 |
| CSRF | 三层 | SameSite=Lax + 服务端 Origin 校验 + Server Actions 内建同源校验(页面内数据操作经 Server Actions 进程内调用 `packages/core`;对外 REST 凭 API key 鉴权,不受 CSRF 影响) |
| Step-up | 10 分钟窗口 | 敏感能力(数据导出、退款、删除活动、改安全设置)要求 10 分钟内完成过一次 passkey 或 magic link 重验证 |
| 权限变更 | 会话 id 轮换 | 角色授予/回收、SSO 强制开启时,相关用户会话立即失效重建 |

用户可在账户页看到设备列表(UA、IP 归属地、最后活跃时间)并远程注销单个或全部会话;每次新设备登录发送通知邮件。API key 与 OAuth 客户端凭证面向机器调用,见第 10 章。

## 6.4 权限模型:两级角色与能力矩阵

权限分两级:**组织级角色**决定你对组织(租户)本身的控制权,**活动级角色**决定你在某一场活动内能做什么。两级角色都不直接参与鉴权——它们只是**能力(capability)集合的预设**,鉴权代码只认能力,不认角色名。这保证了未来增删角色不动任何业务代码。

组织级角色共四个:

| 角色 | 能力概述 |
| --- | --- |
| Owner | 全部能力;唯一可转让所有权、删除组织、管理计费的角色;组织至少保留一名 |
| Admin | 创建/归档活动、管理成员与组织级设置(域名、SSO、品牌),不含计费与删除组织 |
| Member | 无默认能力;仅作为「可被邀请进活动团队」的名录存在 |
| Billing | 仅查看与管理订阅、发票、支付方式;看不到任何活动数据 |

活动级预设角色四个:**组织者**(该活动的全权负责人)、**协作者**(内容与日常操作,不碰钱、团队与批量导出)、**审稿人**(只见被分配的投稿)、**志愿者**(现场签到与胸牌,只见签到视图必需字段)。完整能力矩阵如下,✓ 为预设授予,— 为不授予:

| 域 | 能力 | 说明 | 组织者 | 协作者 | 审稿人 | 志愿者 |
| --- | --- | --- | --- | --- | --- | --- |
| 活动 | `event.view_draft` | 查看未发布的活动内容 | ✓ | ✓ | ✓ | ✓ |
| 活动 | `event.edit` | 编辑活动信息与页面内容 | ✓ | ✓ | — | — |
| 活动 | `event.publish` | 发布 / 下线活动 | ✓ | — | — | — |

| 活动 | `event.delete` | 删除活动(需 step-up) | ✓ | — | — | — |
| 团队 | `team.manage` | 邀请 / 移除成员、分配角色 | ✓ | — | — | — |
| 注册 | `registration.view` | 查看报名列表与完整详情 | ✓ | ✓ | — | — |
| 注册 | `registration.review` | 审批 / 拒绝 / 候补转正 | ✓ | ✓ | — | — |

三条矩阵之外的规则:第一,组织者要写评审必须同时被指派为审稿人,且通过利益冲突申报(见第 4 章)——能力矩阵刻意不给组织者 `review.write`,避免「既当运动员又当裁判」在默认配置下发生。第二,双盲开启时 `submission.view_all` 的响应会在序列化层剥离作者字段,直到进入录用阶段。第三,志愿者的 `checkin.perform` 返回的是专用签到 DTO(姓名、票种、签到状态、饮食标记),拿不到邮箱与自定义字段全文。

能力与预设在代码中是单一事实源:

```ts
// packages/auth/src/capabilities.ts(节选)
export const CAPABILITIES = [
  'event.view_draft', 'event.edit', 'event.publish', /* ... 共 28 项 */
] as const;
export type Capability = (typeof CAPABILITIES)[number];

export const EVENT_ROLE_PRESETS = {
  organizer:    [/* 除 review.write 外全部 */],
  collaborator: ['event.view_draft', 'event.edit', 'registration.view',
                 'registration.review', 'registration.edit', 'form.edit',
                 'checkin.perform', 'badge.print', 'announcement.send',
                 'schedule.edit', 'design.edit', 'email.compose', 'files.manage'],
  reviewer:     ['event.view_draft', 'review.write'],
  volunteer:    ['event.view_draft', 'checkin.perform', 'badge.print'],
} satisfies Record<EventRole, Capability[]>;

// event_role 表存的是能力数组快照,而非角色名 ——
// 组织者可基于预设勾选增减,存出来的就是一个自定义角色。
export async function can(
  actor: Actor, capability: Capability, resource: OrgScoped,
): Promise<boolean> { /* 见第 12 章授权中间件 */ }
```

> **设计要点**:角色是给人看的 UI 概念,能力是给代码看的鉴权原语。自定义角色 = 勾选框改一改预设,不引入任何新机制;权限编辑器直接由 `CAPABILITIES` 常量渲染,永不失同步。

## 6.5 多租户组织模型

组织(organization)即租户。单机自托管是「恰好只有一个组织」的多租户实例,SaaS 与自托管跑同一套代码,没有条件编译。隔离机制自下而上四层:

1. **模式层**:所有业务表携带 `organization_id NOT NULL` 外键,复合索引一律以 `(organization_id, ...)` 打头(见第 9 章)。
2. **查询层**:业务代码不允许直接使用裸 `db`,必须通过 `scopedDb(orgId)` 获得的包装实例,所有查询自动追加租户谓词;ESLint 规则禁止在 `apps/api/src/modules` 内 import 裸连接。
3. **鉴权层**:`can()` 的第一个判据就是资源与 actor 的组织归属,跨租户访问在能力检查之前即返回 404(不泄露资源存在性,见第 12 章)。
4. **资源层**:对象存储按 `org/{orgId}/event/{eventId}/...` 前缀隔离,预签名 URL 的签发路径同样经过 `can()`。

每个组织附带配额与限流参数(SaaS 按套餐、自托管默认不限),包括:并行活动数、存储容量、邮件日发送量、API 速率档位、自定义域名数(域名与白标见第 7 章)。用户可属于多个组织,顶栏组织切换器切换的只是 UI 上下文——每个请求自带目标组织 id,服务端逐请求校验成员关系,不存在「切换后忘记检查」的状态残留。

## 6.6 账户合并、数据导出与注销

**合并**解决的是访客时代留下的碎片:同一个人可能有三个邮箱对应的三条 `person`。合并流程:

1. 用户在账户页发起「添加邮箱」,对目标邮箱走一次 magic link 验证——只有证明控制权才能合并,防止抢占他人记录。
2. 系统列出该邮箱名下的报名、投稿、票据供确认。
3. 单事务内将 `person` 的关联行(registration、submission、order 等)重指到主 `user`,旧 `person` 标记 `merged_into`,旧访问链接全部作废。
4. 写入审计事件 `account.merge`(见第 12 章),并向两个邮箱各发一封通知,给出 72 小时申诉入口。

**导出**:账户页一键发起,BullMQ 任务汇出该用户名下全部个人数据(JSON 为主、报名记录附 CSV),打包后生成 24 小时有效的下载链接,邮件送达;每次导出记审计。这同时是 GDPR 可携权的实现(见第 12 章)。

**注销**采用「30 天冷静期 + 差异化清理」:发起后账户立即锁定登录、进入倒计时(期间登录一次即撤销注销);到期后按数据类别分别处理:

| 数据类别 | 注销后处理 | 依据 |
| --- | --- | --- |
| 个人资料、passkey、OAuth 绑定、会话 | 硬删除 | 无保留义务 |
| 报名记录 | 匿名化(姓名邮箱置为占位符,统计字段保留) | 组织者的历史统计完整性 |
| 已发表投稿 / 归档演讲 | 内容保留,署名按用户注销前的选择保留或改为「已注销用户」 | 学术记录完整性(归档见第 5 章) |
| 订单与发票 | 去标识化后按法定年限保留 | 财税法规 |
| 审计日志 | 保留,主体 id 换为假名映射 | 安全责任追溯(见第 12 章) |

若用户是某组织唯一 Owner,注销被阻断并提示先转让所有权;匿名化任务与保留期调度由 worker 统一执行,时间参数见第 12 章 12.3 节。
